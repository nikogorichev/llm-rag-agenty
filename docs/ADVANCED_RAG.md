# Продвинутые архитектуры RAG — справочник и шпаргалка

Справочник к **`modules/05b-advanced-rag/`**. Модуль 05 строит наивный RAG (chunk → embed → retrieve → rerank → generate → cite). Это следующий уровень: четыре именованные архитектуры, каждая из которых добавляет **обратную связь** или **другой индекс** для устранения конкретного сбоя в разомкнутом конвейере.

# # Таблица выбора по проблеме

| Ваша проблема                                                      | Что выбрать             | Что добавляет                                       |
| ------------------------------------------------------------------- | ------------------------ | ---------------------------------------------------- |
| Правильный чанк существует, но поиск его не находит (местоимения, контекст) | **Contextual Retrieval** | самодостаточные чанки _до_ эмбеддинга                |
| Система галлюцинирует, когда корпус не содержит ответа              | **Corrective RAG**       | оценщик + откат к rewrite/web-search                   |
| Лишний поиск по закрытым вопросам; необоснованные ответы проходят незамеченными | **Self-RAG**             | адаптивный поиск + шлюзы релевантности и поддержки   |
| Ответ требует связывания фактов из разных документов (multi-hop)   | **GraphRAG**             | граф entity/relation + обход                         |
| "Какие темы во всем корпусе?" (глобальный запрос)                   | **GraphRAG (global)**    | сводные описания сообществ + map-reduce (вне рамок здесь) |

Эти подходы комбинируются. В продакшен-стеках часто используют **Contextual embeddings + contextual BM25 + reranking** (модуль 04/05) и оборачивают результат в контур управления **CRAG или Self-RAG**, а для multi-hop/global подмножества запросов применяют **GraphRAG**.

# # 1. Contextual Retrieval (Anthropic, 2024)

**Проблема.** Чанкинг разрушает контекст. "Оно выросло на 3%." — _что_ выросло? Существительные, которые позволяют найти чанк, находятся в _других_ чанках документа.**Решение.** Во время индексации для каждого чанка запросите у LLM контекст из 1–2 предложений, который помещает его в документ, **добавьте** его в начало чанка и получите эмбеддинги для _дополненного_ текста (и проиндексируйте для BM25). Сохраните _исходный_ текст для генерации — эмбеддированный текст и отображаемый текст не обязаны совпадать.```
embed(  "[ctx: From Acme's Q3 2024 report, on quarterly revenue.] It grew 3%..."  )
show (  "It grew 3% year over year..."  )   # generator sees the clean original
```- **Результат (Anthropic):** снижение частоты неудач при поиске top-20 примерно на 35% (contextual embeddings), на ~49% при добавлении контекстуальных BM25, на ~67% при добавлении реранкера поверх.
- **Стоимость:** один дешевый вызов LLM на чанк, оплачивается один раз при индексации. **Используйте prompt-cache для документа**, чтобы предельные затраты на чанк были минимальны.
- **Подвох:** не давайте контексту _замещать_ чанк — добавляйте в начало (prepend), не перезаписывайте. Держите контексты короткими, иначе они будут доминировать в embeddings.

# # 2. Корректирующий RAG / CRAG (Yan et al., 2024)

**Проблема.** Наивный RAG предполагает, что retrieved == relevant, и генерирует ответ в любом случае.

**Решение.** **Оценщик поиска (retrieval evaluator)** оценивает найденный набор, разделяя на три категории:

| Вердикт   | Триггер                  | Действие                                   |
| --------- | ------------------------ | ------------------------------------------ |
| Верно     | точное релевантное совпадение | уточнить + сохранить хорошие чанки → сгенерировать |
| Неверно   | ничего релевантного      | отбросить → **переписать запрос + веб-поиск**   |
| Неоднозначно | неуверенность         | выполнить оба, объединить                  |

- В статье используется fine-tuned T5-оценщик + "knowledge refinement" (разделение чанков на фрагменты, сохранение релевантных). Мы используем **LLM как судью** (оценка 0–1) и пороги (`≥0.7` / `<0.3`).
- **Ключевая ценность:** система, которая _знает, когда она не знает_, и эскалирует запрос, побеждает систему, которая уверенно ошибается.
- **Подвох:** калибруйте пороги на своем корпусе; слишком низкая планка "Неверно" приводит к ненужным откатам в веб-поиск.

# # 3. Само-RAG (Asai et al., 2023)

**Проблема.** Поиск безусловен; проверка на обоснованность не проводится.

**Решение.** Модель генерирует **токены размышления** для самоконтроля:

| Токен     | Решение                                    |
| --------- | ------------------------------------------ |
| `Retrieve` | выполнять поиск? (пропуск для closed-book) |
| `IsRel`    | этот фрагмент релевантен? (фильтр)         |
| `IsSup`    | подтверждено ли утверждение? (fully/partial/no)   |
| `IsUse`    | ответ полезен? (1–5)                       |- Real Self-RAG **обучает** модель выдавать их. Без бюджета на обучение вы **эмулируете каждый токен вызовом судьи** — идентичный поток управления.
- **Преимущество:** адаптивный поиск (дешевле, меньше отвлекающего контекста) + самопроверка, которая помечает необоснованные ответы вместо того, чтобы отправлять их.

**CRAG vs Self-RAG:** CRAG — фиксированный пайплайн с одним внешним оценщиком для _поиска_. Self-RAG — это _сама модель_, пошагово управляющая поиском **и** критикующая _собственную генерацию_. Self-RAG более детализирован, но более «разговорчив» (больше вызовов LLM).

# # 4. GraphRAG (Microsoft, 2024)

**Проблема.** Векторный top-k возвращает чанки, похожие на запрос. Для многоходовых вопросов («какой коллега X получил награду?») и глобальных вопросов («основные темы?») не существует единственного «наиболее похожего» чанка — ответ — это _путь_ или _сводка_.

**Решение.** Постройте **граф знаний**: LLM извлекает тройки `(entity, relation, entity)` → сущности — это узлы, отношения — рёбра.

- **Локальный / многоходовой поиск:** найти сущности запроса, BFS их окрестность, генерировать ответ по связанным тройкам. (Именно это реализует модуль 05b, **вручную — без `networkx`/`graphrag`**: граф — это словарь списков смежности.)
- **Глобальный поиск / выявление смыслов:** кластеризовать граф (Leiden) на сообщества, суммировать каждое, применить map-reduce к сводкам. (Выходит за рамки; см. «Углубляемся».)
- **Подводный камень:** качество извлечения определяет всё — несогласованность имен сущностей («Marie Curie» vs «M. Curie») фрагментирует граф. Нормализуйте ключи сущностей.
- **Оптимальный вариант для продакшена:** найти исходные узлы векторным поиском, затем пройти по графу для расширения — гибрид граф + вектора.
