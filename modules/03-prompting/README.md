# Модуль 03 — Промптинг и паттерны

Самая точка приложения усилий в приложениях на базе LLM (Large Language Model) — это не модель, а промпт.
Но «prompt engineering» (инжиниринг промптов) кажется магией, пока не подойти к нему эмпирически:
сформулировать гипотезу, проверить на небольшом размеченном наборе данных, замерить точность, выбрать лучший.

В этом модуле промпт-инжиниринг рассматривается как дисциплина, а не тёмное искусство.
В итоге у вас будет рабочий механизм eval, который позволит сравнить два варианта промптов
по числам — тот же принцип, который лежит в основе внутренних оценок промптов у Anthropic и OpenAI.

# # Концепции

## # Шаблоны и роли

Простая конкатенация строк для промптов чревата скрытыми ошибками (опечатка в имени переменной = молчаливый сбой).
Крошечный помощник вроде `render_template("Hello {{name}}", {"name": "Alice"})` делает структуру шаблона
явной и сразу сообщает об отсутствующих ключах.

Роли:

- **system** — инструкции с высшим уровнем доверия. Задают персону, ограничения, формат вывода.
  Пользователю сложно их переопределить.
- **user** — запрос. Это то, на что модель «отвечает».
- **assistant** — ответ модели. В few-shot промптах сюда вставляют _примеры_ ответов ассистента.

## # Few-shot против zero-shot

**Zero-shot:** только описание задачи. Модель обобщает на основе обучающих данных.
**Few-shot:** описание задачи + k пар примеров `(user, assistant)` перед реальным запросом.
Модель считывает паттерн из примеров.

Компромиссы:

- Больше примеров → обычно выше точность.
- Больше примеров → больше токенов → больше стоимость.
- Убывающий эффект после 5–10 примеров.
- Один удачно подобранный пример часто превосходит три заурядных.

## # Chain-of-thought (CoT)

Просьба модели «подумать шаг за шагом» перед ответом заставляет её выдавать промежуточные
рассуждения, которые иначе остались бы скрытыми. Это значительно повышает точность на задачах, требующих
многошаговой логики, арифметики или причинно-следственных рассуждений.

Цена: ответы в стиле CoT намного длиннее (больше выходных токенов). Используйте выборочно на сложных задачах.

## # Самосогласованность (Self-consistency)

Семплируйте один и тот же CoT промпт N раз при `temperature > 0` (чтобы каждый прогон шёл по другому
пути рассуждений) и выберите финальный ответ большинством голосов. Отдельные семплы могут ошибаться; голосование
усредняет шум.Стоимость: N × токенов CoT. Используйте, когда точность важнее скорости или стоимости.

## # Парсинг вывода и защитные механизмы

Цикл исправления:

1. Отправить prompt.
2. Попытаться распарсить вывод в требуемый формат.
3. При ошибке: добавить неудачный ответ + сообщение с исправлением в историю.
4. Снова вызвать модель. Повторить до max_retries.
5. Сдаться и выбросить исключение после исчерпания попыток.

Этот паттерн встречается в каждом продакшен-решении на базе LLM.

## # Стенд для оценки промптов

Без измерений prompt engineering — это гадание. Стенд для оценки (eval harness):

1. Загрузить размеченный датасет (10 примеров в `eval_dataset.json`).
2. Определить варианты промптов.
3. Запустить каждый вариант на каждом примере.
4. Оценить по точности (predicted label == expected label).
5. Вывести сравнительную таблицу. Выбрать победителя.

Это тот же принцип, что лежит в основе крупномасштабных оценок — просто в масштабе, который можно прогнать локально за несколько минут.

# # Задачи

## # Задача 1 🟢 — Шаблоны и роли

**Цель:** Создать переиспользуемый помощник для шаблонов промптов и протестировать его на двух задачах.

**Шаги:**

1. Откройте `py/01_templates.py` и `ts/01-templates.ts`.
2. Реализуйте `render_template` / `renderTemplate` — заменяйте плейсхолдеры `{{key}}`.
   Выбрасывайте исключение при отсутствующих ключах.
3. Реализуйте `call_with_system` — помощник, который отправляет системное + пользовательское сообщение и возвращает ответ.
4. Используйте `TEMPLATES["summarise"]`, чтобы суммировать примерный текст в 2 предложения.
5. Используйте `TEMPLATES["classify"]`, чтобы классифицировать три текста. Выведите исходный ответ — обратите внимание на шум.

**Критерии приёма:**

- `render_template("Hello {{name}}", {"name": "Alice"})` → `"Hello Alice"`.
- Отсутствующий ключ вызывает понятную ошибку.
- Вызовы суммирования и классификации возвращают реальный вывод модели.

## # Задача 2 🟡 — Few-shot против zero-shot

**Цель:** Сравнить точность классификации с 0, 1 и 3 примерами; вывести таблицу.

1. Откройте `py/02_few_shot.py` и `ts/02-few-shot.ts`.
2. Определите 3 `FEW_SHOT_EXAMPLES` (по одному на класс).
3. Реализуйте `build_zero_shot_messages` и `build_few_shot_messages`.
4. Для каждого тестового ввода запустите все три варианта и выведите результаты в таблице.
5. Понаблюдайте: становятся ли метки лучше? Соблюдает ли модель формат строже?

**Критерии приёма:**- В таблице выводятся результаты для каждого входа в режимах 0-shot, 1-shot и 3-shot.
- Вы сможете объяснить, почему few-shot помог (или не помог) в этой задаче.

## # Task 3 🟡 — Chain-of-thought & self-consistency

**Цель:** Реализовать CoT prompting и голосование по принципу self-consistency для математических/логических задач.

**Шаги:**

1. Откройте `py/03_cot.py` и `ts/03-cot.ts`.
2. Реализуйте `build_direct_prompt` (только ответ, без рассуждений).
3. Реализуйте `build_cot_prompt` (думайте пошагово, затем "Final answer: X").
4. Реализуйте `extract_final_answer` для извлечения ответа из CoT-ответа.
5. Реализуйте `majority_vote(answers: list[str])`.
6. Для каждой задачи: запустите direct, single CoT и self-consistency (N=3). Выведите результаты.

**Критерии приёма:**

- В CoT-ответах присутствуют видимые шаги рассуждений.
- `extract_final_answer` корректно извлекает ответ из CoT-текста.
- `majority_vote` возвращает наиболее часто встречающийся ответ среди N примеров.
