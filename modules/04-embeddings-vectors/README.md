# Модуль 04 — Embeddings (векторные представления) & векторы

> **Метки глубины** 🟢 уровень приложения · 🟡 собрать один компонент вручную · 🔴 с нуля

Embeddings превращают смысл в геометрию. Как только текст попадает в векторное пространство, задача «найти связанные фрагменты» превращается в «найти близкие точки» — именно это двигатель, на котором работают поиск, RAG (Retrieval-Augmented Generation), рекомендации и обнаружение аномалий.

В этом модуле мы собираем этот двигатель послойно: сначала вручную, затем с настоящей векторной базой данных, а затем изучаем, как разбиение на чанки и гибридный поиск влияют на то, что вы получаете в результате.

# # Концепции

## # Что такое embedding (векторное представление)?

Модель embedding отображает строку в список чисел с плавающей точкой фиксированной длины — _вектор_ в многомерном пространстве (часто 768 или 1536 измерения). Модель обучается так, чтобы семантически похожие строки располагались близко друг к другу в этом пространстве. «Кошка сидела на коврике» и «Кошка отдыхала на ковре» будут иметь векторы, расположенные гораздо ближе друг к другу, чем любой из них к «Фондовый рынок резко упал».

## # Косинусное сходство

Стандартная метрика расстояния — **косинусное сходство**:```
cosine(a, b) = dot(a, b) / (|a| × |b|)
```Она измеряет угол между двумя векторами независимо от их длины.
Большинство embedding-моделей L2-нормализуют свой вывод (`|v| = 1`), что сводит
косинусное расстояние к обычному скалярному произведению — быстро и просто.

Значения: 1 = одинаковое направление, 0 = ортогональные (не связаны), −1 = противоположное.

## # Полный перебор против ANN

При _n_ документах размерности _d_ полный перебор для поиска похожих занимает O(n·d) на
запрос. Для 1 млн документов × 1536 измерений это 1,5 млрд умножений на
запрос — слишком медленно. Алгоритмы **Approximate Nearest Neighbour** (ANN), такие как
**HNSW** (Hierarchical Navigable Small World), строят граф на этапе индексации и
на этапе запроса обходят лишь малую часть векторов. Компромисс: небольшой риск
пропустить истинного ближайшего соседа, на практике обычно несущественный (recall@10

> 99 % при типичных настройках).

## # Чанкование

Embedding-модели имеют лимит токенов (обычно 256–512 токенов). Если поместить
целый 10-страничный документ в один embedding, будут потеряны детали. **Чанкование** разбивает
документ на меньшие пересекающиеся фрагменты. Основные компромиссы:

| Стратегия           | Плюс                               | Минус                             |
| ------------------- | ---------------------------------- | --------------------------------- |
| Фиксированный размер | Простота, предсказуемость          | Может разрывать предложение       |
| По предложениям     | Естественные границы               | Переменный размер чанков          |
| С пересечением      | Без потери контекста на границах   | Больше места хранения, больше embedding'ов |

Хороший размер чанка зависит от окна вашей embedding-модели и характера запросов
(точные фактические вопросы vs. широкие обобщения).

## # Гибридный поиск и Reciprocal Rank Fusion

Плотный поиск хорошо справляется с _семантическими_ запросами («найди текст о
кошачьих» находит «кошек»). Разреженный поиск (BM25, Best Matching 25) хорош для
запросов с _точным совпадением_ — коды продуктов, имена моделей, редкие
технические термины. **Гибридный поиск** запускает оба подхода и объединяет
отсортированные списки с помощью **Reciprocal Rank Fusion** (RRF):```
RRF_score(d) = Σ_ranker  1 / (k + rank(d, ranker))
````k = 60` — это стандартная константа сглаживания. RRF не требует калибровки оценок от разных ранжировщиков — он использует только порядок ранжирования, что делает его устойчивым.

## # Task 3 🟡 — Chunking strategies

**Goal:** Увидеть, как границы чанков влияют на качество поиска.

**Files:**

- `py/03_chunking_strategies.py`
- `ts/03-chunking-strategies.ts`

**Steps:**1. Реализуйте `fixed_size_chunker` — разделение по границам слов каждые ~N символов.
2. Реализуйте `sentence_chunker` — группировка по N предложений в один чанк.
3. Реализуйте `overlapping_chunker` — чанки фиксированного размера с перекрывающимся окном.
4. Test-хarness встраивает один и тот же запрос по всем трём стратегиям и показывает,
   какой чанк из какой стратегии наиболее релевантен.

**Критерии приёма:**

- Каждый чанкер возвращает непустой список непустых строк.
- Для длинного документа получается больше чанков при меньшем размере чанка.
- При перекрытии всегда получается не меньше чанков, чем при фиксированном размере.

**Размышление:** Запустите с `chunk_size=100` и `chunk_size=500`. Какие запросы
выигрывают от меньших чанков? Какие — от бо́льших?
