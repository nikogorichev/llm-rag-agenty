# Модуль 05 — RAG (Retrieval-Augmented Generation)

> **Depth tags** 🟢 app-level · 🟡 build-one-piece-by-hand · 🔴 from-scratch

RAG — это наиболее широко применяемый шаблон в реальных приложениях на основе LLM (Large Language Model). Вместо того чтобы дообучать (fine-tuning) модель на ваших приватных данных (дорого, долго и требует экспертизы в области ML — Machine Learning), вы храните данные в поисковом хранилище (retrieval store) и внедряете соответствующие фрагменты в prompt в момент запроса. Модель остаётся универсальной; знания остаются актуальными и проверяемыми.

В этом модуле мы с нуля построим полный RAG-пайплайн: разбиение на чанки (chunk), создание эмбеддингов (embed), поиск (retrieve), генерацию (generate), цитирование (cite) и оценку (evaluate). Затем мы улучшим базовую версию с помощью реранкинга и HyDE (Hypothetical Document Embeddings), а также оценим качество, используя подход LLM-as-judge.

Prereq: сначала завершите модуль 04 (концепции VectorStore, chunking и гибридного поиска используются здесь).

# # Концепции

## # Пайплайн RAG```
Document corpus
   │
   ▼  (offline, once)
[Chunk] ──► [Embed] ──► [Vector Store / Index]
                                │
                                │ (online, per query)
   Question ──► [Embed query] ──┘
                    │
                    ▼
               [Retrieve top-k chunks]
                    │
                    ▼
         [Stuff chunks into prompt]
                    │
                    ▼
               [LLM generates answer]
                    │
                    ▼
              Answer + Citations
```### Почему RAG снижает галлюцинации

Базовая LLM экстраполирует данные из обучающей выборки. Когда её спрашивают о том, чего она не знает (или о том, что изменилось после обучения), она угадывает — часто уверенно, но неверно. RAG накладывает ограничения на модель: системный промпт гласит «отвечай ТОЛЬКО на основе предоставленного контекста». Задача модели — извлечение и суммаризация, а не придумывание.

Оговорка: RAG не устраняет галлюцинации полностью. Модель всё ещё может игнорировать контекст, неправильно его прочитать или смешать контекст со знаниями из обучения. Именно поэтому важна оценка из задания 3.

## # Качество поиска — узкое место

Самый частый сценарий сбоя: _нужный чанк не был найден_. Если ответа нет в контекстном окне, модель не сможет сгенерировать его правильно. Поэтому стратегия разбиения на чанки из модуля 04, гибридный поиск и ранжирование этого модуля так важны: всё это направлено на то, чтобы в промпт попадали нужные чанки.

Практическое правило: если ваша RAG-система даёт неверные ответы, сначала проверяйте поиск, а не генерацию.

## # Ранжирование (Reranking)

Поисковик первой стадии (bi-encoder) кодирует запрос и отрывок _отдельно_, затем вычисляет косинусное расстояние в пространстве эмбеддингов. Это быстро, но неточно — он не может смоделировать взаимодействие между конкретной фразой в запросе и конкретной фразой в отрывке. Кросс-энкодер (или LLM-ранжировщик) видит их вместе и работает гораздо лучше — ценой скорости.

Практический паттерн: получить широкие кандидаты (top-50) с помощью быстрого bi-энкодера, затем переранжировать с помощью LLM или кросс-энкодера, оставить top-5 для генерации.

## # HyDE — Hypothetical Document Embeddings

Проблема: вопрос «Что такое HNSW (Hierarchical Navigable Small World)?» существует в пространстве вопросов, а чанки корпуса — в пространстве ответов. Разрыв в эмбеддингах приводит к промахам при поиске.

Решение: попросить LLM написать _гипотетический_ ответ, получить его эмбеддинг и использовать этот эмбеддинг гипотезы для поиска. Гипотеза вроде «HNSW — это основанный на графах индекс ANN (Approximate Nearest Neighbor)...» будет совпадать с чанками корпуса про HNSW гораздо лучше, чем исходный вопрос.

HyDE добавляет один вызов LLM на каждый запрос. Он лучше всего работает, когда формы поверхностей запроса и ответа различаются (технические Q&A, запросы на иностранном языке по английской документации).### Оценка RAG (LLM как судья)

Три метрики, вдохновлённые [RAGAS](https://docs.ragas.io/):

| Метрика                    | Вопрос                              | Как оценивать                                                                  |
| -------------------------- | ----------------------------------- | ------------------------------------------------------------------------------ |
| **Faithfulness** (Истинность) | Каждый ли факт опирается на контекст? | Разбить ответ на утверждения; проверить каждое по контексту. Оценка = % подтверждённых. |
| **Context relevance** (Актуальность контекста) | Релевантны ли полученные чанки?      | Оценить от 0 до 10 полезность контекста для ответа.                            |
| **Answer relevance** (Актуальность ответа)     | Отвечает ли ответ на вопрос?         | Оценить от 0 до 10 точность соответствия ответа вопросу.                      |

Все три метрики используют LLM в качестве судьи — значит, судью можно ввести в заблуждение правдоподобным, но неверным текстом. Считайте оценки сигналом, а не ground truth.

## # Метрики поиска: recall@k, MRR, NDCG (заметки к собеседованию)

LLM-as-judge оценивает _генерацию_; сам ретривер оценивается классическими
метриками ранжирования на размеченном наборе (query → relevant chunks):

- **Recall@k** — доля запросов, у которых релевантный чанк встречается где-то в
  топ‑k. Первая цифра для настройки: если правильный чанк не в топ‑k, ничего
  ниже по пайплайну не спасёт.
- **MRR (Mean Reciprocal Rank)** — среднее от `1/rank` для _первого_ релевантного
  результата (1.0 = всегда первый, 0.5 = обычно второй). Важная метрика, когда
  достаточно одного хорошего чанка — а так в большинстве RAG.
- **NDCG (Normalized Discounted Cumulative Gain)** — сумма градуированной релевантности,
  дисконтированной по `1/log₂(rank+1)`, нормализованная относительно идеального порядка.
  Важная метрика, когда релевантность градуирована (очень/отчасти/нет) и важны
  несколько результатов.

Практический рецепт: измеряйте recall@k, чтобы выбрать k и ретривер; MRR — чтобы
оценить реранкер (в модуле 05 задание 2 должно поднять MRR); а NDCG приводите,
когда на собеседовании спрашивают «как вы оцениваете поиск?». В финальном проекте
M2 milestone используется MRR@5 именно по этой причине.

## # ЦитированияЦитирование делает RAG проверяемым. Вместо одного непрозрачного ответа вы получаете список утверждений, каждое из которых связано с исходным чанком. Это позволяет вам:

- Обнаруживать галлюцинации (утверждение без валидной ссылки)
- Отслеживать происхождение каждого факта
- Создавать UI (пользовательский интерфейс), который подсвечивает процитированные фрагменты

**Goal:** Реализовать метрики LLM-as-judge (LLM как судья): faithfulness (верность), context relevance (релевантность контекста), answer relevance (релевантность ответа).

# # Going deeper- **RAGAS:** Библиотека [RAGAS](https://docs.ragas.io/) автоматизирует вычисление всех трёх метрик с помощью лучших промптов и усреднения. Замените самописные оценщики на RAGAS и сравните результаты.
- **Контекстное сжатие:** Вместо того чтобы вставлять в промпт целые чанки, попросите LLM извлечь только те предложения, которые относятся к вопросу. Это уменьшит длину промпта и уровень шума.
- **Многошаговый RAG (Multi-hop RAG):** Некоторые вопросы требуют нескольких этапов поиска (например: «Кто основал компанию, которая создаёт HNSW?» — сначала найдите чанк про HNSW, чтобы определить компанию, затем найдите чанк про основателя). Реализуйте цикл, который определяет момент, когда нужен второй поиск.
- **Потоковые ответы:** В задании 1 замените `provider.chat()` на `provider.chat_stream()` и выводите ответ токен за токеном.
- **Переранжирование кросс-энкодером:** Вместо LLM используйте специализированный кросс-энкодер из HuggingFace (`cross-encoder/ms-marco-MiniLM-L-6-v2`), это значительно дешевле за вызов.
- **Оценка достоверности без LLM:** Используйте модели NLI (Natural Language Inference), чтобы проверить, следует ли каждое утверждение из контекста — вызовы LLM не требуются.
