# Модуль 05b — Продвинутые архитектуры RAG

> **Теги глубины** 🟢 уровень приложения · 🟡 собрать один элемент вручную · 🔴 с нуля

В Модуле 05 мы собрали pipeline **наивного RAG (Retrieval-Augmented Generation)** (chunk → embed → retrieve → rerank → generate → cite) и сделали его измеримо лучше за счёт переранжирования и HyDE (Hypothetical Document Embeddings). Этот pipeline _разомкнутый (open-loop)_: он делает один запрос поиска, доверяет всему, что вернулось, и генерирует ответ. У него нет ответа на три вопроса, на которых ломаются реальные RAG-системы:

1. **«Что если чанк бессмыслен сам по себе?»** — «Он вырос на 3%». Вырос на _чём_, в _каком_ квартале? При эмбеддинге чанка без контекста информация теряется.
2. **«Что если поиск вернул мусор?»** — наивный RAG всё равно генерирует, а LLM (Large Language Model) уверенно галлюцинирует на основе постороннего контекста.
3. **«Что если для ответа нужны два прыжка?»** — «Какой коллега Мари Кюри тоже получил две Нобелевские премии?» Ни один чанк не содержит ответа; нужно _соединить_ факты из разных документов.

В этом модуле — четыре известные архитектуры, которые поле разработало, чтобы ответить на эти вопросы. Каждая добавляет **петлю обратной связи или структуру**, которых нет у наивного RAG.

> **Требование:** завершите модуль 05 (минимум задачи 1–2). В этом модуле предполагается, что вы уже можете объяснить «chunk → embed → retrieve → generate» и один раз писали косинусный ретривер. Здесь мы используем этот ретривер как чёрный ящик.

# # Ментальная модель (один абзац)Naive RAG — это прямая линия. Любая архитектура здесь превращает эту линию в **петлю** или меняет **индекс**. **Contextual Retrieval** исправляет _индекс_: она переписывает каждый чанк так, чтобы он был самодостаточным _до_ создания embeddings, чтобы поиск вообще мог его найти. **Corrective RAG (CRAG)** добавляет _оценщик после поиска_: чанки оцениваются, и если они слабые, происходит корректировка курса (переписывание запроса, откат к веб-поиску) вместо генерации поверх шума. **Self-RAG (Self-Reflective RAG)** переносит решения _внутрь петли генерации_: сама модель решает, делать ли retrieval, оценивает релевантность каждого фрагмента и критикует, действительно ли поддерживается её собственный ответ. **GraphRAG (Graph-based RAG)** полностью отбрасывает плоский векторный список и строит _граф_ сущностей и отношений, так что multi-hop-запросы превращаются в обходы графа. Тот же retriever внизу; принципиально иной поток управления вокруг него.```
  Naive RAG:     query ──▶ retrieve ──▶ generate ──▶ answer   (no feedback)

  Contextual:    [index time] chunk + doc-context ──▶ embed   (better recall)
  CRAG:          query ──▶ retrieve ──▶ GRADE ──┬─ good ─▶ generate
                                                └─ bad ──▶ rewrite + web search ──▶ generate
  Self-RAG:      query ──▶ retrieve? ──▶ judge each passage ──▶ generate ──▶ self-critique
  GraphRAG:      query ──▶ find entities ──▶ traverse graph ──▶ generate over connected facts
```---

# # Концепции

## # 1. Contextual Retrieval — исправьте чанк перед тем, как создавать эмбеддинг

Чанк вроде _"The model scored 88.7% on the benchmark."_ практически бесполезен в изоляции: какая модель? какой бенчмарк? Запрос _"Claude's MMLU (Massive Multitask Language Understanding) score"_ не найдёт его, потому что в чанке нет ни слова "Claude", ни "MMLU". Слова, которые сделали бы его находкой, находятся в **других** чанках документа.

**Contextual Retrieval** (Anthropic, 2024) решает это на этапе индексации: для каждого чанка попросите LLM написать краткий (1–2 предложения) контекст, который помещает чанк _в контекст исходного документа_, затем **добавьте этот контекст в начало чанка перед созданием эмбеддинга** (и перед индексацией BM25 (Best Matching 25)). Чанк, который вы сохраняете для поиска, становится таким:```
[context: This is from Anthropic's 2024 model card, describing Claude 3.5
 Sonnet's evaluation results.]  The model scored 88.7% on the benchmark.
```Теперь embedding содержит недостающие существительные, и запрос совпадает. Anthropic сообщает, что это снизило частоту **ошибок** при топ-20 поиске примерно на 35% (только контекстуальные embeddings), на 49% (добавление контекстуального BM25) и на 67% (добавление реранкера сверху). Цена: один дешёвый вызов LLM для каждого чанка на этапе индексации — платится один раз и амортизируется по всем будущим запросам. Кэширование промпта с документом делает это почти бесплатным.

> **Ключевая идея:** чанк, который вы _эмбеддите_, и чанк, который вы _показываете генератору_, могут не совпадать. Contextual Retrieval эмбеддит _аугментированный_ чанк, но может хранить исходный текст для генерации.

## # 2. Corrective RAG (CRAG) — оцениваем поиск, а затем исправляемся

Фатальное допущение наивного RAG: _retrieved == relevant_ (найденное == релевантное). CRAG (Yan et al., 2024) разрушает его с помощью **легковесного оценщика поиска**, который оценивает, насколько хорошо найденный набор отвечает на запрос, выдавая один из трёх вердиктов:

| Вердикт      | Значение                                   | Действие                                           |
| ------------ | ------------------------------------------ | -------------------------------------------------- |
| **Correct**  | хотя бы один сильно релевантный чанк       | уточнить + оставить хорошие чанки, генерировать    |
| **Incorrect**| ничего релевантного                         | отбросить всё; **откатиться** (web-поиск)          |
| **Ambiguous**| неуверенно                                  | сделать и то, и другое — сохранить чанки _и_ откатиться |

«Коррекция» — это тот самый цикл, которого не хватает наивному RAG: когда локальный корпус не может ответить, CRAG **переписывает запрос** и обращается к внешнему источнику вместо того, чтобы галлюцинировать. Оценщик — это сердце системы: быстрая модель (или дообучённый T5 в статье; мы используем подход LLM-as-judge, который вам уже знаком), которая возвращает оценку релевантности для каждого чанка, а мы разбиваем их по порогам на три категории.

> **Почему это важно:** RAG-система, которая _знает, когда она не знает_, может сказать «я не нашёл это» или эскалировать запрос — это гораздо безопаснее, чем уверенный неправильный ответ.

## # 3. Self-RAG — позволяем модели управлять поиском и критиковать саму себяCRAG оценивает поиск извне. **Self-RAG** (Asai et al., 2023) переносит каждое решение _внутрь_ цикла генерации, используя **reflection tokens** (токены рефлексии) — специальные токены, которые генерирует модель для управления своим поведением:

| Reflection token | Вопрос, на который он отвечает                           |
| ---------------- | ------------------------------------------------------- |
| **Retrieve**     | Нужно ли вообще выполнять поиск для этого запроса?      |
| **IsRel**        | Является ли этот найденный отрывок релевантным?         |
| **IsSup**        | Подтверждается ли мой сгенерированный тезис отрывком?   |
| **IsUse**        | Действительно ли ответ полезен (1–5)?                   |

В настоящем Self-RAG модель _обучают_ генерировать эти токены. Мы не можем делать fine-tuning, поэтому **эмулируем каждый токен рефлексии через LLM-as-judge с промптом** — тот же поток управления, но без обучения. (В статье у токена `Retrieve` на самом деле три значения — `yes` / `no` / `continue`, где `continue` повторно использует уже найденный отрывок; наша эмуляция да/нет сворачивает это третье значение.) Преимущество — **адаптивный поиск**: для _«Сколько будет 2+2?»_ модель отвечает `Retrieve=No` и полностью пропускает этап поиска в индексе (быстрее, дешевле, нет нерелевантного контекста); для _«Что отчёт за Q3 говорил об оттоке?»_ она выполняет поиск, отфильтровывает релевантные отрывки с помощью `IsRel`, генерирует ответ, а затем проверяет с помощью `IsSup`, что каждое предложение подтверждено данными.

> **CRAG vs Self-RAG:** CRAG — это фиксированный пайплайн с навешанным сверху оценщиком. Self-RAG — это _сама модель_ принимает на каждом шагу решение, делать ли поиск и доверять ли полученному. CRAG корректирует поиск; Self-RAG ещё и критикует генерацию.

## # 4. GraphRAG — когда ответ находится _между_ документами

Векторный RAG извлекает top-k фрагментов, _наиболее похожих на запрос_. Это не срабатывает для двух типов запросов:

- **Multi-hop (многошаговые):** _«Какой физик, работавший с Резерфордом, позже возглавил Манхэттенский проект?»_ Ни один фрагмент не содержит всю цепочку; ответ — это _путь_.
- **Global / «смыслообразование»:** _«Какие основные темы прослеживаются во всех этих отчётах?»_ Ни один отдельный фрагмент не является «наиболее похожим»; ответ — это _сводка по всему корпусу документов_.**GraphRAG** (Microsoft, 2024) строит **граф знаний** вместо (или вместе с) плоским векторным индексом: LLM извлекает **триплеты (сущность, отношение, сущность)** из каждого чанка; сущности становятся **узлами**, отношения — **рёбрами**. Теперь:

- **Локальный поиск** (multi-hop): найти сущности в запросе, пройтись по их рёбрам, чтобы собрать _связанные_ факты, и сгенерировать ответ по этой окрестности.
- **Глобальный поиск** (themes): кластеризовать граф на сообщества, суммаризировать каждое, затем выполнить map-reduce над суммаризациями — но это выходит за рамки данного модуля; мы реализуем локальный/multi-hop поиск.

Полный Microsoft GraphRAG также выполняет обнаружение сообществ по алгоритму Leiden и иерархическую суммаризацию. Мы строим **ядро**: извлечение → граф → multi-hop обход, **вручную** (🔴 — без `networkx`, без пакета `graphrag`; граф — это просто словарь списков смежности, и суть в том, чтобы реализовать его самостоятельно).

LLM_PROVIDER=openai      # or ollama / nvidia / lmstudio — anything with embed()
                         # for Task 1. Tasks 2–4 work on any provider.
```## Дополнительные зависимости Python

Отсутствуют — помимо базовой установки. Эти задачи используют только `llm_core` и стандартную библиотеку. (Граф для задачи 4 намеренно реализован вручную.)```bash
uv sync                  # base deps are enough
```
