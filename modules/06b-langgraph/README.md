# # Зачем нужен LangGraph

Простой `while`-цикл (модуль 06, задание 1) работает, пока вам не понадобится что-то из следующего списка; в этот момент вы начинаете изобретать собственный фреймворк:

| Вам нужно…                                                   | Цена самостоятельной реализации           | Что даёт LangGraph                           |
| ------------------------------------------------------------ | ----------------------------------------- | --------------------------------------------- |
| Возобновить запуск после сбоя / на следующий день            | самостоятельно сериализовать и перезагружать всё состояние | **checkpointer** + `thread_id`                |
| Приостановиться для одобрения человеком перед вызовом инструмента | bespoke flag plumbing                     | `interrupt()` / `interrupt_before`            |
| Стримить токены _и_ шаги в UI (User Interface)               | ручной fan-out                            | `stream_mode` (`values`/`updates`/`messages`) |
| Разветвлять / повторять / разветвлять диалог                 | учёт снепшотов                            | **time travel** поверх чекпоинтов             |
| Несколько специалистов, маршрутизирующих друг в друга        | ad-hoc dispatch                           | **`Command(goto=…)`** handoff + подграфы      |
| Видеть каждое прошедшее сообщение                            | print-debugging                           | трассировка в LangSmith                       |LangGraph — это **рантайм**, а не библиотека для промптинга. Это типизированный,
с контрольными точками (checkpointer) и стримингом конечный автомат для рабочих процессов LLM (Large Language Model). LangChain (цепочки,
обёртки для чат-моделей, `@tool`) — это _зависимость_, на которую он опирается для уровня модели,
но движок графа и есть продукт.

# # Ментальная модель (один абзац)

Приложение LangGraph — это **граф над общим объектом состояния**. **Ноды** — это простые
функции `(state) -> partial_state_update`. **Рёбра** определяют, какая нода запустится следующей,
— фиксированные рёбра (`A -> B`) или **условные рёбра** (функция возвращает имя следующей ноды). **Состояние** — это типизированный словарь, поля которого — это **каналы**; каждый
канал имеет **редюсер** (reducer), который определяет, как обновление ноды мёрджится (по умолчанию — перезапись,
_add (добавление)_ для списков сообщений). Вы `compile()` граф в `app`,
опционально с **checkpointer**; затем `invoke`/`stream` его с помощью `config`,
который содержит `thread_id`. Всё остальное в этом модуле — это функционал, наложенный поверх этого ядра: персистентность, прерывания, стриминг, подграфы, передача управления (handoff), перемещение во времени.```
        ┌─────────┐  tool_calls?  ┌─────────┐
START ──▶│  agent  │──────yes─────▶│  tools  │
        └─────────┘               └─────────┘
             │  no                     │
             ▼                         │
            END  ◀── (cycle back) ─────┘
```Эта схема — **предсобранный ReAct агент** — функция `create_react_agent(model, tools)`
собирает именно его. Используйте предсобранный вариант там, где он подходит, и стройте граф вручную там, где нужен контроль. Умение делать _и то, и другое_ — важный признак для собеседований.

# # Concepts

## # 1. State, channels, reducers

Состояние (state) — это контракт между узлами. Узел возвращает только те ключи, которые хочет изменить; LangGraph объединяет каждый ключ с помощью **reducer’а** этого канала:

- reducer по умолчанию = **побеждает последняя запись** (overwrite).
- `add_messages` (Python) / messages reducer (TS) = **добавление + дедупликация по id**, плюс он обновляет простые словари до объектов `Message`. Именно поэтому канал сообщений «просто растёт» без конкатенации с вашей стороны.

Пользовательские reducer’ы позволяют каналу _накапливать_ значения (суммировать счётчик, объединять множества, вести список). Выбор правильного reducer’а для каждого канала — и есть большая часть «проектирования состояния». `MessagesState` (Python) / `MessagesAnnotation` (TS) — это предсобранное состояние, которое представляет собой просто `{ messages }` с append‑reducer’ом — большинство агентов начинают отсюда.

## # 2. Nodes, edges, conditional edges, `ToolNode`

- **Node**: `def agent(state): return {"messages": [model.invoke(state["messages"])]}`.
- **Normal edge**: `add_edge("tools", "agent")` — всегда переходить от tools к agent.
- **Conditional edge**: `add_conditional_edges("agent", route)`, где `route(state)` возвращает имя следующего узла (или `END`). Это и есть поток управления агента.
- **`ToolNode`** (предсобранный): узел, который читает `tool_calls` из последнего AI‑сообщения, запускает каждый инструмент и возвращает `ToolMessage`. **`tools_condition`** (предсобранный) — соответствующий роутер: «к tools, если есть tool_calls, иначе END». Вместе они заменяют те ~30 строк, которые вы писали вручную в модуле 06.

## # 3. Persistence — checkpointers & threads

Скомпилируйте с **checkpointer’ом**, и каждый супер‑шаг будет сохранён:```python
app = workflow.compile(checkpointer=InMemorySaver())
app.invoke(inputs, {"configurable": {"thread_id": "user-42"}})
```**`thread_id`** — это одна сессия/один запуск. Один и тот же thread → следующий вызов `invoke` продолжается с того места, где закончился предыдущий (сохранённые сообщения подгружаются автоматически).

Так вы получаете **память между ходами** _и_ **возможность возобновления после перезапуска процесса**. Для настоящей персистентности поменяйте `InMemorySaver` на `SqliteSaver` / `PostgresSaver` (отдельные пакеты). Чекпоинтер также — основа для прерываний и «путешествий во времени»; без них это невозможно.

## # 4. Human-in-the-loop — `interrupt()`

Самый востребованный фич LangGraph для продакшена. Два варианта:

- **Статический**: `compile(..., interrupt_before=["tools"])` ставит на паузу _перед_ нодой tools при каждом проходе. Осмотрите/отредактируйте стейт, затем возобновите, вызвав `invoke(None, config)`.
- **Динамический**: вызовите `interrupt(payload)` _внутри ноды_. Граф останавливается, передаёт `payload` в ваше приложение (например, «разрешить отправку этого письма?») и **возобновляется с той же самой строки**, когда вы вызываете `invoke(Command(resume=answer), config)`. Нода перезапускается с начала, но `interrupt` возвращает переданное значение.

Используйте для этапов одобрения, промптов при недостающих данных и редактирования перед выполнением. Это работает только потому, что чекпоинтер сделал снимок состояния в точке паузы.

## # 5. Потоковая передача (Streaming)

Граф генерирует поток; `stream_mode` задаёт гранулярность:

| mode       | что выдаёт                                            | для чего                              |
| ---------- | ----------------------------------------------------- | ------------------------------------- |
| `values`   | полное состояние после каждого шага                   | «покажи текущее состояние»            |
| `updates`  | только дельту, которую вернула каждая нода            | UI с пошаговым прогрессом             |
| `messages` | **токены LLM** по мере генерации (+ метаданные)       | чат‑UI с посимвольным выводом         |
| `custom`   | всё, что вы отправляете через stream writer           | прогресс‑бары для инструментов и т.п. |

Можно передать **список** режимов. Режим `messages` как раз обеспечивает эффект печати «как в ChatGPT» изнутри мульти-нодного графа.

## # 6. ПодграфыСкомпилированный граф можно **использовать как узел** внутри большего графа. Это подграф.
Он нужен, чтобы (а) переиспользовать целого агента как один шаг, и (б) держать отдельные схемы состояний
(родитель делит только те каналы, имена которых совпадают). Стримьте с `subgraphs=True`, чтобы видеть внутренние шаги.
Так большие системы остаются компонуемыми, а не превращаются в один 40-узловой граф-спагетти.

## # 7. Multi-agent — передача управления с помощью `Command`

В модуле 06 задание 5 мы вручную реализовали схему планировщик → исполнители → синтезатор. Примитив LangGraph — **`Command`**: узел может вернуть `Command(goto="researcher", update={...})`, чтобы за один ход обновить состояние **и** перейти к другому узлу. Паттерны:

- **Supervisor**: один узел-маршрутизатор решает, какой исполнитель запустится следующим, через `Command(goto=…)`; исполнители возвращают управление супервизору. (`langgraph-supervisor` / `create_react_agent` строят это за вас, но важно понимать сам примитив `Command`.)
- **Swarm / сеть**: исполнители передают управление _напрямую_ друг другу.

Передача управления — это просто «обновить разделяемое состояние + перейти к другому узлу». Это предложение — уже полный ответ для собеседования.

## # 8. Time travel

С чекпоинтером вы получаете полную историю:

- `get_state(config)` → текущий снепшот (`StateSnapshot`: значения, следующие узлы, `checkpoint_id`).
- `get_state_history(config)` → все прошлые чекпоинты, от новых к старым.
- Продолжить работу со **старого** чекпоинта, передав его `checkpoint_id` в конфиге — граф **форкнет** новую ветку из этой точки.
- `update_state(config, values)` → изменить состояние (записать через редьюсеры каналов), чтобы создать исправленный чекпоинт, и продолжить.

Это даёт вам отладку («replay с шага 3»), ветвление по сценарию «что если» и редактирование человеком с продолжением — всё бесплатно, как только включено персистентное хранилище.

## # 9. Где платформа встраивается (знать названия)

Здесь вы это строить не будете, но на собеседованиях часто называют эти термины:- **LangSmith** — панель для трассировки, оценки и наблюдаемости (set `LANGCHAIN_TRACING_V2=true`).
- **LangGraph Studio** — визуальный отладчик графов; пошаговое выполнение по узлам, редактирование состояния, «путешествие во времени» в UI.
- **LangGraph Platform / Server** — развёртывание с хостингом: превращает ваш скомпилированный граф
  в API (Application Programming Interface) с управляемым чекпоинтером, планированием и очередью задач.
