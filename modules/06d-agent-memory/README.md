# Модуль 06d — Память агента

> **Метки глубины** 🟢 уровень приложения · 🟡 собрать один компонент вручную · 🔴 с нуля

В модуле 06 агент получил ровно одну память — **черновик** (Task 3), а в 06b
был добавлен **устойчивый персистент тредов** с помощью чекпоинтера LangGraph. Это реальные решения, но продакшен-агенты (и собеседования) различают целую **таксономию**: эпизодическую (история разговора), семантическую (база знаний), процедурную (паттерны рабочих процессов), entity-память, память-сводки — а также дисциплину **управления** памятью
(encode → store → retrieve → inject → forget), а не просто её чтение.

Рамка, на которой строится этот модуль:

- **Memory-augmented (с дополнением памятью)**: память _происходит_ с агентом. История дописывается,
  ретривер сбрасывает в промпт всё, что нашёл, ничего не обновляется и не забывается.
  Это работает до тех пор, пока контекст не раздуется, факты не устареют, а шумы не заглушат сигнал.
- **Memory-aware (осведомлённый о памяти)**: агент (или его обвязка) _управляет своим когнитивным состоянием_.
  Чтение выполняется в фиксированном порядке до вызова модели, запись — после него,
  у каждого типа памяти есть механизм поиска и правило забывания, а всё соблюдает лимит токенов.

Вы собираете осведомлённую о памяти версию, по одному типу памяти за раз, а затем компонуете их в `MemoryManager`, чей контекст остаётся в рамках бюджета, в то время как базовая версия без управления его превышает.

Всё работает **оффлайн** через тот же шов, что и в модуле 06c:```
ChatFn = (messages) => string        # Python: Callable[[list[dict]], str]
```- С флагом `--stub` harness подставляет **детерминированную фейковую модель** — без сети, без API-ключа, с точными проверками (stub возвращает историю, которую видел, возвращает фиксированный валидный JSON сущности и выдаёт фиксированные саммари).
- Без флага тот же `ChatFn` собирается из `get_provider().chat` (Python: `from llm_core import get_provider`) / `getProvider().chat` (TypeScript: `from '@learn-ai/llm-core'`) — никогда не жёстко зашитый вендор.

Состояние хранится в локальных JSON-файлах модуля в каталоге `state/` (gitignored, очищается в начале каждого запуска). Детерминизм везде: **фейковые целочисленные часы** для TTL, счётчик whitespace-токенов для бюджетов — никакого `Date.now()`, никакого реального времени.

> **Предварительное условие:** завершите модуль 06 (задания 1 и 3). Вы должны уметь сказать «агент — это цикл» и хотя бы раз собрать scratchpad. 06b (checkpointer, `thread_id`) поможет, но не обязателен — в этом модуле реализуется собственное минимальное персистентное хранилище, чтобы механика памяти оставалась наглядной.

# # Концепции

## # 1. Memory-augmented против memory-aware и таксономия пяти типов

LLM stateless; любой вид «памяти» — это то, что вы строите вокруг вызова модели. Пять типов, которые в production-системах реально называют по имени:| Type           | Human analogy               | Lookup mechanism                         | When read                              | When written                            |
| -------------- | --------------------------- | ---------------------------------------- | -------------------------------------- | --------------------------------------- |
| **Episodic**   | "что случилось"             | по thread + recency (последние _n_ ходов) | каждый ход (программно)               | после каждого хода (программно)         |
| **Semantic**   | "что я знаю"                | по схожести (vector / lexical search)    | каждый ход, с порогом (программно)    | при ingestion / upsert, когда меняются факты |
| **Procedural** | "как я действую"            | загружается целиком (system prompt, skills) | каждый ход (программно)               | редко — курируется вручную, не за ход   |
| **Entity**     | "кого/что я знаю"           | по ключу: (имя, тип)                     | каждый ход (программно)               | после ходов, где упоминаются сущности   |
| **Summary**    | "суть того, что случилось"  | замещает архивированные ходы; расширяемый | каждый ход (программно)               | при compaction, когда история превышает лимит |

Блокнот из модуля 06 был однослотовым гибридом всех пяти типов; checkpointer из модуля 06b обеспечивает только episodic персистентность. В этом модуле каждый тип реализуется как отдельное хранилище с собственными правилами чтения/записи — именно это разделение и означает «memory-aware». (Мы используем четыре из пяти: procedural memory — это system prompt / файлы навыков, которые вы уже курируете вручную; он присутствует в таксономии, чтобы его можно было назвать, но реализовывать что-то каждый ход не нужно.)

## # 2. Жизненный цикл: чтение до вызова, запись после

Один memory-aware ход — это фиксированный пайплайн вокруг единого вызова модели:```
encode → store → retrieve → inject → forget

per turn:
    forget:    evict stale records (TTL)          # before anything else
    retrieve:  episodic → semantic → entities → summaries   (fixed read order)
    inject:    assemble the context, under a token budget
    (model call)
    encode+store:  write the user turn + reply, extract entities,
                   summarise old history if over budget
```Инвариант: **чтение из памяти выполняется ПЕРЕД вызовом модели, запись в память —
ПОСЛЕ него.** Модель не изменяет хранилище в процессе вызова; жизненным циклом
управляет обвязка (harness).

Вторая важная граница: какие операции являются **программными** (их всегда делает
обвязка), а какие — инициированными **агентом** (решает модель, через вызов tool):

| Operation                               | Who triggers it                | Why                                                          |
| --------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| Загрузка недавней истории (эпизодической) | programmatic                   | нужно на каждом шаге; модель не может запросить то, чего не видит |
| Поиск в базе знаний                     | programmatic                   | дёшево, с порогом — вставляется только то, что проходит по релевантности |
| Загрузка известных сущностей            | programmatic                   | мало и всегда полезно                                         |
| Разворачивание саммари в исходные шаги  | agent-triggered                | дорого; только когда агенту действительно нужны детали      |
| Веб-поиск / внешний поиск               | agent-triggered                | медленно, затратно, обычно не нужно                           |
| Компактификация (саммари старых шагов)   | programmatic (по бюджету) или agent-triggered | кто-то должен отслеживать бюджет                            |

Неправильно провести границу в одну сторону — получаете **раздувание контекста**
(разворачиваете каждый саммари и ищете в вебе «на всякий случай» — модель тонет);
в другую — **потерю контекста** (модели никогда не показали нужную историю, и она
не знает, что её нужно запросить).

## # 3. Качество поиска: шум, устаревание, обновление при записи

Чтение базы знаний — это то место, где системы с расширенной памятью тихо деградируют:- **Зашумлённый поиск.** Top-k _всегда_ возвращает k результатов — даже если k-й результат является семантически близким, но отвлекающим ("поисковая служба использует Elasticsearch" для вопроса о базе данных оформления заказа). Исправление — **порог релевантности**: ранжируем, берём top-k, затем отбрасываем всё, что ниже `min_score`. Пустой результат лучше, чем правдоподобный, но неверный.
- **Устаревание / TTL.** Факты устаревают (промокоды, заморозки релизов, дежурства). Добавляйте в записи, чувствительные ко времени, поле `created_at` и исключайте их, когда `now - created_at > ttl`. В задаче 4 используется **фиктивный целочисленный таймер**, чтобы исключение было точным и проверяемым.
- **Update-on-write (upsert).** Когда факт меняется, запись его как _новой_ записи оставляет старую версию в хранилище — а поиск с радостью выдаст обе, позволяя старой правде конкурировать с новой. Ключевые записи должны иметь стабильный id и **замещаться при записи**; то же правило относится к сущностям (одинаковое имя + тип → обновляем факт, а не добавляем дубликат).

Мы ранжируем с помощью офлайн-метода **bag-of-words cosine** из 06c (скалярное произведение векторов количеств по общим словам, делённое на нормы), чтобы каждый счёт был детерминированным — уроки о качестве поиска без изменений переносятся на реальные embeddings (модуль 04).

## # 4. Сводная память, JIT-расширение и бюджет токенов

История растёт линейно; контекстное окно — нет. **Сводная память** сжимает старые раунды в одну запись — но дисциплина такая: **маркируй, не удаляй**: оригиналы остаются в хранилище с тегом `archived_by = summary_id`. Сводка заменяет их в собираемом контексте; когда агенту действительно нужны детали, **just-in-time расширение** (`expand_summary(summary_id)`) восстанавливает оригинальные раунды дословно. Сжатие становится обратимым, поэтому перестаёт пугать.

Это делает **бюджет токенов** принудительно исполняемым: сначала считаются секции с фиксированной стоимостью (семантические попадания, сущности, сводки), а оставшийся бюджет заполняется эпизодическими раундами от новых к старым — так _самая старая_ история первой возвращается к своей сводке. В модуле 16 (Context Engineering) работу с бюджетом рассматривают как отдельную тему; здесь вы реализуете минимальную версию, необходимую любому агенту.
