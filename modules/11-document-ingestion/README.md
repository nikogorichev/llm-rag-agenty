# Модуль 11 — Приём документов

> **Метки глубины** 🟢 уровень приложения · 🟡 собрать один компонент вручную

Приём документов — это входной контур данных для любого конвейера RAG (Retrieval-Augmented Generation). В этом модуле вы изучите проектирование, которое определяет качество поиска: разбор реальных форматов документов, очистку от шума, разбиение на чанки по структуре (а не по произвольному количеству символов) и инкрементное обновление индекса.

**Предварительные требования:** сначала завершите модуль 05 (RAG). В этом модуле предполагается наличие чистого, заранее отформатированного текста; этот модуль показывает, как прийти к нему из хаоса реального мира.

# # Концепции

## # Почему приём документов — это 80% RAG-проекта

RAG-демо отлично работает на аккуратном текстовом файле. Продуктовая система работает с PDF (Portable Document Format), отсканированными с бумаги, HTML (HyperText Markup Language) страницами, полными навигационных меню и баннеров cookie, документами Word с встроенными изображениями и Markdown-вики с непоследовательными уровнями заголовков. Каждый формат добавляет шум, а шум ухудшает поиск. Ответ может быть настолько хорош, насколько хороши извлечённые чанки, а чанки могут быть настолько хороши, насколько хорош извлечённый текст.

Пропорция: около 20% инженерии продуктового RAG — это настройка поиска и генерации; около 80% — это создание надёжного конвейера приёма, который обрабатывает edge cases.

## # Разбор форматов| Формат         | Основная сложность                                                                                              | Библиотека                                          |
| -------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **PDF**        | Многоколонная верстка, колонтитулы на каждой странице, отсканированные PDF (нужен OCR — распознавание текста)   | pypdf / pdfplumber (Python); pdf-parse (TypeScript) |
| **HTML**       | Навигация, реклама, баннеры cookie, мусор из `<script>` засоряет основной текст                                 | beautifulsoup4 (Python); cheerio (TypeScript)       |
| **Markdown**   | Чистый текст, но синтаксис заголовков (`#`, `**`, `` ` ``) путает embeddings                                    | stdlib regex                                        |
| **DOCX / EPUB** | Проприетарные бинарные форматы; нужны python-docx / ebooklib                                                    | выходит за рамки данного материала                  |

Эмпирическое правило: сначала парсим в простой текст, затем очищаем, потом разбиваем на чанки. Держите парсинг и очистку отдельными этапами, чтобы каждый можно было тестировать.

## # Очистка

Сырой текст от парсеров содержит:

- **Boilerplate**: ссылки навигации, уведомления о cookie, футеры, номера страниц.
- **Мусор пробелов**: несколько идущих подряд пустых строк, смешанные отступы.
- **Артефакты форматирования**: Markdown `##`, `**bold**`, HTML-сущности `&amp;`.
- **Почти дубликаты**: один и тот же абзац, процитированный в нескольких местах.

Эвристики очистки, которые нужно знать:

- **Фильтр по длине строки**: одиночные короткие строки, похожие на элементы навигации ("HOME", "Contact Us"), можно отбрасывать.
- **Ключевые слова boilerplate**: "Cookie Policy", "Terms of Service" и т. д.
- **Шингловая дедупликация**: вычисляем схожесть Жаккара между fingerprint'ами абзацев; если схожесть > 0.8, дубликат отбрасываем.

## # Чанкинг с учётом структуры

Наивное чанкинг фиксированного размера из модуля 04 рассматривает документ как плоский поток слов. Это может разрезать заголовок от его тела или вопрос от ответа.

**Section-aware chunking** (чанкинг с учётом секций) вместо этого:1. Определяет границы заголовков (Markdown `#`, `##`, `###`; HTML `<h1>` – `<h3>`).
2. Сохраняет каждый раздел как одну логическую единицу.
3. Разбивает на под-фрагменты (sub-chunks) только если размер раздела превышает лимит токенов для embedding-модели.
4. Добавляет заголовок в начало каждого под-фрагмента, чтобы название раздела всегда оставалось в контексте — критически важно для поиска.```
Document
├── # Introduction       → Chunk 0  (heading + intro prose)
├── ## Why RAG?          → Chunk 1  (heading + body)
│   └── (long body)      → Chunk 1a, 1b  (sub-chunked; each starts with "## Why RAG?")
└── ## The Pipeline      → Chunk 2
```### Метаданные для каждого чанка

Каждый чанк должен содержать:

| Ключ                | Зачем                                                                                        |
| ------------------- | -------------------------------------------------------------------------------------------- |
| `source`            | Путь к файлу или URL — для указания источника и отслеживания актуальности                   |
| `section`           | Текст заголовка — для фильтрации и отображения                                              |
| `page`              | Номер страницы в PDF — для ссылок на страницы PDF                                            |
| `ingested_at`       | Временная метка в формате ISO — для выявления устаревших данных                             |
| `estimated_tokens`  | Для планирования использования контекстного окна                                            |

## # Инкрементальное индексирование

Повторное создание embedding для всех документов при каждом запуске медленное и дорогое. Инкрементальное индексирование использует хеш содержимого для каждого документа:```
hash(current text)  ==  hash(stored in manifest)
      ↓ yes                      ↓ no
   skip (no API call)      re-embed + update manifest
```Манифест — это небольшой JSON-файл, содержащий маппинг `source → {hash, timestamp, model}`.
При каждом запуске: хешируем каждый файл, сравниваем с манифестом, отправляем на embeddings только изменения.

В промышленном масштабе это превращается в паттерн upsert в векторной БД (например,
`upsert` в Qdrant с `id = hash(chunk_text)` — существующие векторы остаются без изменений;
новые и изменённые заменяют старые).

## # Задание 5 🟡 — Поиск с учётом прав доступа

**Цель:** При ингесте прикреплять к документам метаданные доступа (владелец, группа, видимость) и применять их при поиске, чтобы запрос для данного пользователя возвращал только те чанки, которые ему разрешено видеть. Усилить цитирование страниц/разделов, добавляя в метаданные чанков `source`, `section` и `page`.

**Файлы:**

- `py/05_permissions_aware.py`
- `ts/05-permissions-aware.ts`

**Шаги:**1. Реализуйте `tag_access()` / `tagAccess()` — создайте `PermissionedChunk`
   с текстом чанка, вектором эмбеддинга, ACL (владелец/группы/видимость) и
   полями для цитирования (`source`, `section`, `page`).
2. Реализуйте `user_can_access()` / `userCanAccess()` — верните True/false на
   основе правил видимости: `public` → всегда; `private` → только владелец;
   `group` → владелец или участник группы.
3. Реализуйте `cosine_similarity()` / `cosineSimilarity()` — скалярное
   произведение норм, защитите от деления на ноль (векторы нулевой длины).
4. Реализуйте `retrieve_for_user()` / `retrieveForUser()` — поддерживает два режима:
   - **Pre-filter** (`pre_filter=True`): ограничьте набор кандидатов доступными
     чанками ДО оценки. Предпочтительно в продакшене (быстрее, позволяет
     избежать оценки документов, которые пользователь никогда не увидит).
   - **Post-filter** (`pre_filter=False`): оцените все чанки, затем оставьте только
     доступные результаты. Приведено для сравнения — результаты должны совпадать
     с pre-filter.
5. Запустите проверочный сценарий для пользователей `alice`, `bob`, `carol`,
   `guest` и убедитесь, что каждый видит только разрешённые чанки, а в
   библиографических ссылках указаны `source`, `section` и (при наличии) `page`.

**Acceptance:**

- `guest` (участник `["all"]`) видит только `public`-документы и документы группы `all`.
- `bob` (участник `["finance", "exec", "all"]`) видит документы finance/exec, но не
   документы ops или `private`-документ board.
- Pre-filter и post-filter возвращают одинаковые ID чанков в том же порядке.
- Каждый `RetrievalResult` печатает строку цитирования с `source` и `section`.
- Сценарий выводит сводную таблицу доступа без ошибок.

  сохраняйте вложенность H1 > H2 > H3 в метаданных, чтобы можно было фильтровать по секции верхнего уровня.
- **Разбиение по предложениям:** Вместо подсчёта слов делите по границам предложений
  (используйте `nltk.sent_tokenize` или простой эвристический подход «точка-пробел»)
  и группируйте N предложений в один чанк. Сравните качество выдачи с хarness'ом оценки из модуля 05.
- **Полная интеграция RAG:** Передайте чанки из задач 3 и 4 в RAG-пайплайн из модуля 05.
  Замените встроенный CORPUS_DOCS на реальные документы и оцените, улучшится ли качество выдачи.
- **Дедупликация в масштабе:** Подход с шинглами и Жаккаром имеет сложность O(n²) по числу абзацев.
  Для больших корпусов посмотрите на
  [MinHash LSH (Locality-Sensitive Hashing)](https://en.wikipedia.org/wiki/MinHash) (доступен в
  `datasketch`), который ищет почти дубликаты за O(n).
- **Веб-краулинг:** Расширьте задачу 1, чтобы принимать URL, загружать страницу, переходить по ссылкам
  на один уровень вглубь и собирать небольшой корпус. Не забудьте проверять `robots.txt`.
