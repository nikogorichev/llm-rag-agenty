# Введение в RAG

Retrieval-Augmented Generation (RAG) — это методика, которая объединяет систему поиска
с большой языковой моделью (LLM) для создания основанных на фактах ответов.

# # Зачем нужен RAG?

Большие языковые модели обучаются на статических снимках интернета. Они не
знают о событиях после даты отсечки обучающей выборки и не могут получить доступ
к вашим приватным документам. Fine-tuning может восполнить пробел в знаниях, но это
медленный, дорогой процесс, требующий экспертизы в ML.

RAG решает эту задачу иначе: хранить знания вне модели, в хранилище данных (retrieval store),
и внедрять в prompt только релевантные фрагменты в момент запроса. Задача модели
сокращается с «знать всё» до «прочитать предоставленный текст и ответить на вопрос».

# # Пайплайн

1. **Инжест (Ingestion, офлайн):** парсинг документов, очистка текста, разбиение на чанки,
   создание embeddings для каждого чанка и сохранение их в векторной базе данных.
2. **Ретривел (Retrieval, онлайн):** создание embedding для вопроса пользователя, поиск top-k
   наиболее похожих чанков и их извлечение.
3. **Генерация:** формирование prompt, который включает найденные чанки в качестве контекста,
   и запрос к LLM ответить, используя только этот контекст.

# # Инжест — это 80% работы

Распространённое заблуждение: RAG — это просто «дать LLM несколько документов».
На практике этап инжеста отнимает большую часть инженерного времени в боевых проектах.

- PDF содержат колонтитулы, многостраничные макеты и таблицы, которые ломают наивное
  извлечение текста.
- HTML-страницы окружены навигацией, рекламой и шаблонным текстом, который заглушает
  полезный сигнал.
- Markdown чист, но заголовки задают семантические секции, которые не должны разрываться
  между чанками.

Правильная реализация инжеста — определение формата, удаление мусора, осознанное разбиение на чанки
с учётом структуры — то, что отличает игрушечный RAG-демо от продакшен-системы.

# # Стратегии чанкования

| Стратегия | Для чего лучше всего подходит |
| --- | --- |
| Фиксированный размер (по словам/символам) | Простота; хороший базовый вариант |
| На основе предложений | Запросы на естественном языке |
| На основе секций/заголовков | Структурированные документы (мануалы, вики) |
| С перекрытием (Overlapping) | Предотвращает потерю контекста на границах |

Правильный размер чанка зависит от лимита токенов вашей embedding-модели (обычно
256–512 токенов) и характера ваших запросов.## Важность метаданных

Каждый чанк должен содержать метаданные, чтобы вы могли:
- Фильтровать по источнику или дате на этапе поиска.
- Показывать пользователю, из какого документа взят факт (атрибуция).
- Отслеживать актуальность и отключать устаревшие чанки при инкрементальном переиндексировании.

Минимально полезные метаданные: `source`, `page` (для PDF), `section` (для заголовков),
`ingested_at`.
