# Модуль 12 — Text-to-SQL

> **Теги глубины** 🟢 уровень приложения · 🟡 реализовать один кусок вручную

Не все корпоративные данные хранятся в документах. Показатели продаж, записи о клиентах,
складские остатки и логи событий живут в реляционных базах данных — и LLM (большая языковая модель) может выполнять к ним запросы
на обычном английском, если вы предоставите ей нужный контекст схемы.

Этот модуль учит вас строить пайплайн NL (Natural Language, естественный язык) → SQL (Structured Query Language), который будет одновременно полезным и безопасным:
генерировать SQL из вопросов, заземлять генерацию метаданными схемы и примерами строк,
защищать от разрушительных запросов, самовосстанавливаться при ошибках и маршрутизировать
между SQL и RAG (Retrieval-Augmented Generation) в зависимости от намерения вопроса.

---

# # Концепции

## # Естественный язык → SQL

Основная идея проста: дать LLM определения ваших таблиц и попросить её написать SQL.
Разница в качестве между наивным промптом и тщательно проработанным — огромна.

| Качество промпта                                   | Типичные проблемы                              |
| -------------------------------------------------- | ---------------------------------------------- |
| "Write SQL to answer: {question}"                  | Придуманные имена колонок, неверные таблицы, нет JOIN |
| + имена таблиц                                      | Лучшие имена таблиц, но колонки всё ещё неверны |
| + имена колонок и типы                             | В основном верно для запросов к одной таблице  |
| + примеры строк и подсказки по JOIN                | Обрабатывает несколько таблиц, выбирает правильные значения колонок |
| + few-shot примеры                                 | Надёжно обрабатывает агрегации и граничные случаи |

Вывод: заземление схемы (schema grounding) — не опция. Модель без схемы будет уверенно галлюцинировать имена колонок.

## # Заземление схемы

Хороший промпт со схемой включает:

1. **Имя таблицы и имена колонок с типами** — `orders(id INTEGER, customer_id INTEGER, ...)`.
2. **Enum-значения** — `status: 'pending' | 'shipped' | 'delivered' | 'cancelled'`.
3. **Связи внешних ключей** — `orders.customer_id → customers.id`.
4. **3–5 примеров строк на таблицу** — чтобы модель понимала реалистичные значения.
5. **Явные шаблоны JOIN** — распространённые соединения, записанные полностью.
6. **Один-два few-shot примера** — пара «вопрос + верный SQL».Генерация описания схемы на основе активной базы данных (с помощью `PRAGMA table_info`
и `SELECT ... LIMIT 3`) гарантирует, что оно остаётся синхронизированным автоматически.

## # Безопасность: зачем нужно валидировать сгенерированный SQL

LLM может выполнить запрос вроде «delete all orders», если ему это позволить.
Инъекция в стиле RAG во входных данных пользователя также может обмануть модель,
заставив её выдать деструктивный SQL. Два обязательных ограничения:

1. **Whitelist только для чтения:** проверяйте, что первое ключевое слово — `SELECT`. Отклоняйте
   `DROP`, `DELETE`, `UPDATE`, `INSERT`, `ALTER`, `CREATE`, `REPLACE`, `TRUNCATE`.
2. **Отклонение состыкованных запросов (stacked queries):** считайте количество точек с запятой. Больше одной — попытка инъекции.
   (`SELECT 1; DROP TABLE users; --` — классический пример.)

Это простые, но эффективные меры. Они не предотвращают все атаки (например, вредоносные
подзапросы, вызывающие проблемы с производительностью), но блокируют самые опасные из них.

## # Самоисправление

Сгенерированный LLM SQL иногда не проходит с первого раза: неверное имя столбца,
синтаксическая ошибка, несовместимая функция SQLite. Вместо того чтобы показывать
ошибку пользователю, отправьте её обратно в LLM в рамках диалога из нескольких раундов:```
System: [schema prompt]
User:   "How many orders were placed in Q1 2024?"
Asst:   "SELECT count(*) FROM orders WHERE order_date BETWEEN '2024-01-01' AND '2024-04-01';"
User:   "That SQL produced this error: ... Please fix it."
Asst:   [corrected SQL]
```На практике это исправляет ~70–80% ошибок на первом шаге. Установите `max_retries=2` — если модель не сможет исправить ошибку за 3 попытки, покажите её пользователю.

## # Гибридная маршрутизация: SQL против RAG

Не каждый вопрос пользователя должен отправляться в SQL:

| Question                                                             | Best backend                    |
| -------------------------------------------------------------------- | ------------------------------- |
| "How many orders did Alice place last month?"                        | SQL — точное число из базы данных |
| "What is the average order value by region?"                         | SQL — агрегация по таблице      |
| "What is RAG and how does it work?"                                  | RAG — концептуальные знания     |
| "Why might customers in the West region churn?"                      | RAG — анализ / рассуждения      |
| "Show me Alice's orders and explain why RAG helps personalise them." | Оба подхода                     |

Маршрутизатор классифицирует намерение и отправляет запрос дальше. LLM хорошо подходит для классификации, так как понимает как естественный язык, так и разницу между вопросом о данных и вопросом о знаниях.

**Когда побеждает SQL:** точные числа, количества, агрегации, фильтры по структурированным полям, ранжирование, тренды во времени.

**Когда побеждает RAG:** концептуальные вопросы, инструкции, справочные сведения, анализ, требующий рассуждений над текстом, а не суммирования чисел.

# # Tasks

## # Task 1 🟢 — NL→SQL

**Goal:** Сгенерировать SQL по вопросу, выполнить его и вывести строки.

**Files:**

- `py/01_nl_to_sql.py`
- `ts/01-nl-to-sql.ts`

**Steps:**

1. Реализуйте `generate_sql()` / `generateSql()` — сформируйте prompt на основе схемы, вызовите LLM, верните строку SQL.
2. Реализуйте `extract_sql()` / `extractSql()` — уберите markdown-обрамление и верните единственный SQL-запрос, заканчивающийся на ";".
3. Реализуйте `execute_sql()` / `executeSql()` — откройте `sales.db`, выполните запрос, верните (columns, rows).
4. Реализуйте `query()` — свяжите генерацию и выполнение.
5. Запустите тестовый сценарий; он отвечает на 4 вопроса.

**Acceptance:**- Все 4 вопроса возвращают строки (не исключения).
- Сгенерированный SQL является валидным для SQLite (проверьте, прочитав поле `sql` в выводе).
- "Total revenue from delivered orders" возвращает одно число.

## # Задание 3 🟡 — Safety & repair (безопасность и исправление)

**Goal:** Проверять, что сгенерированный SQL доступен только для чтения, блокировать инъекции и выполнять самостоятельное исправление при ошибках БД.

**Files:**

- `py/03_safety_repair.py`
- `ts/03-safety-repair.ts`

**Steps:**

1. Реализуйте `validate_read_only()` / `validateReadOnly()` — проверьте первое ключевое слово и отсканируйте на наличие запрещённых слов; при неудаче вызывайте исключение `UnsafeSQLError` / `UnsafeSqlError`.
2. Реализуйте `validate_no_stacked_queries()` / `validateNoStackedQueries()` — отклоняйте запросы с несколькими точками с запятой.
3. Реализуйте `repair_sql()` / `repairSql()` — многоходовой диалог для исправления некорректного SQL-запроса.
4. Реализуйте `safe_query()` / `safeQuery()` — цепочка: генерация → валидация → выполнение → исправление при ошибке (до `max_retries`).
5. Запустите тестовый набор: 2 безопасных вопроса и 2 вредоносных ввода.

**Acceptance:**- Обычные вопросы выполняются успешно (retries=0 на хорошей модели).
- "DROP TABLE customers" блокируется до любого выполнения в БД.
- "DELETE FROM orders WHERE 1=1" блокируется.
- `UnsafeSQLError` / `UnsafeSqlError` возбуждается (не generic exception) для
  опасных входных данных.

# # Going deeper- **PostgreSQL:** Тот же паттерн NL→SQL работает с PostgreSQL через
  `psycopg2` / `asyncpg`. Что меняется? В системный prompt нужно добавить информацию
  о диалекте PostgreSQL (например, `ILIKE`, приведение типов `::text`, `NOW()` против `datetime()`).
- **Размер схемы:** При наличии 100+ таблиц нельзя уместить всю схему в
  контекстное окно. Добавьте этап выбора таблиц: попросите LLM указать,
  какие 3–5 таблиц релевантны вопросу, и включите в prompt по схеме только их.
- **Параметризованные запросы:** Для пользовательских приложений никогда
  не подставляйте пользовательский ввод в SQL-строки напрямую — используйте
  плейсхолдеры `?` (Python/sqlite3) или `$1` (PostgreSQL).
  Сгенерированный SQL следует проверять на риски интерполяции.
- **Fine-tuning:** Spider и WikiSQL — стандартные бенчмарки для моделей NL→SQL.
  Ознакомьтесь с [DIN-SQL](https://arxiv.org/abs/2304.11015) и
  [DAIL-SQL](https://arxiv.org/abs/2308.15363) — это современные подходы.
- **Полный гибридный RAG + SQL:** Подключите роутер из задания 4 к реальному RAG-пайплайну
  из модуля 05. Замените заглушку `KNOWLEDGE_BASE` на живой поиск
  по векторам и оцените, как улучшится качество маршрутизации.
- **Стриминг результатов:** Для медленных агрегаций по большим таблицам
  отдавайте частичные результаты пользователю, используя паттерн `cursor.fetchmany()` в SQLite.
