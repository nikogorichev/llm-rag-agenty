# # Концепции

## # Prompt vs RAG vs fine-tune — принятие решения

Прежде чем писать хоть строчку кода для fine-tuning, нужно спросить: **действительно ли fine-tuning — подходящий инструмент?** Основные три стратегии:

| Стратегия       | Что добавляет                              | Когда использовать                                             |
| --------------- | ------------------------------------------ | ------------------------------------------------------------- |
| **Prompting**   | Ничего — использует базовую модель         | Новая задача, мало/нет примеров, метки часто меняются          |
| **RAG**         | Внешние знания на этапе inference          | Нужны актуальные или приватные факты, объем знаний велик       |
| **Fine-tuning** | Постоянная адаптация стиля/поведения/задачи | Стабильный тон, приватная схема, жёсткий формат вывода, скорость |

Эмпирическое правило: **начните с prompting, добавьте RAG для знаний, рассматривайте fine-tuning только когда у вас есть сотни чистых примеров и стабильное определение задачи, которое не будет меняться каждый месяц.** Повторный fine-tuning стоит дорого; плохой набор данных порождает модель, которая уверенно делает неправильно.

## # Supervised fine-tuning (SFT (Supervised Fine-Tuning) / instruction tuning)

SFT означает взятие предобученной базовой модели и продолжение её обучения на парах `(prompt, completion)`, которые демонстрируют желаемое поведение. Так GPT-3 стал ChatGPT (InstructGPT): базовая модель уже «знает» язык, а SFT учит его следовать инструкциям.

Формат JSONL, который ожидает OpenAI fine-tuning API:```jsonl
{
  "messages": [
    {
      "role": "system",
      "content": "..."
    },
    {
      "role": "user",
      "content": "..."
    },
    {
      "role": "assistant",
      "content": "..."
    }
  ]
}
```Каждая строка — один обучающий пример. Модель обучается предсказывать ответ `assistant`,
исходя из предыдущих реплик — классическая цель предсказания следующего токена, просто
на ваших примерах, а не на веб-данных.

## # LoRA — Low-Rank Adaptation

Дообучение всех миллиардов параметров дорого и медленно. LoRA (Hu et al., 2021) —
идея, которая сделала локальное дообучение практически применимым:

**Основная идея:** В процессе дообучения _изменение_ весовой матрицы ΔW обычно
имеет низкую внутреннюю размерность (ранг). Вместо того чтобы обновлять полную
матрицу W (размерность [d, d]), LoRA представляет обновление как произведение двух
малых матриц:```
ΔW = B · A     where B ∈ ℝ^{d×r}, A ∈ ℝ^{r×d},  r ≪ d
```Обучаются только B и A; W остаётся замороженным. Прямой проход выглядит так:```
output = W·x + B·A·x = (W + B·A)·x
```**Сравнение количества параметров** для весовой матрицы формы [d, d] ранга r:

| Method         | Parameters |
| -------------- | ---------- |
| Full fine-tune | d²         |
| LoRA           | 2·d·r      |

При d=4096, r=16: full = 16.7M params; LoRA = 131K params — **в 127 раз меньше**.

**QLoRA** (Quantized Low-Rank Adaptation) (Dettmers et al., 2023) добавляет квантование поверх: веса замороженной базовой модели хранятся с точностью 4 бита, чтобы поместиться в потребительский GPU, а адаптеры LoRA обучаются в bfloat16. Это делает возможным fine-tuning модели с 7B параметров на GPU с 16 ГБ.

## # Качество датасета и переобучение

Самая частая ошибка при fine-tuning — плохое качество данных:

- **Слишком мало примеров** (< 50–100): модель запоминает примеры и не обобщает.
- **Несогласованный формат**: если ответы вашего ассистента иногда заканчиваются точкой, а иногда нет, модель учит шум.
- **Утечка метки**: если eval-набор содержит почти точные копии примеров из обучающего набора, ваши метрики слишком оптимистичны.

Признаки переобучения: training loss продолжает падать, но validation loss перестаёт падать (или растёт). Решение: более разнообразные данные или остановка обучения раньше.

## # Task 5 🔴 — Understand LoRA: implement the low-rank update

**Goal:** Реализуйте идею LoRA — представить ΔW как B·A — с нуля, используя только numpy (Python) или обычные массивы (TypeScript). Без ML-фреймворков. Посчитайте, сколько параметров вы экономите, и проверьте прямой проход численно.

**Files:**

- `py/05_lora_scratch.py`
- `ts/05-lora-scratch.ts`

**The harness is runnable. You implement the TODO sections.**

**Steps:**

1. Реализуйте `lora_init()` / `loraInit()` — инициализируйте матрицы:
   - `A` : shape [r, d_in] — случайное нормальное распределение, маленькое std (например 0.01)
   - `B` : shape [d_out, r] — нули (стандартная инициализация LoRA: B=0, чтобы ΔW начинался с нуля)

2. Реализуйте `lora_forward()` / `loraForward()` — вычислите LoRA-адаптированный вывод:```
   output = W @ x + (B @ A) @ x    # or equivalently (W + B@A) @ x
   ```3. Реализуйте `count_params()` / `countParams()` — верните
   `{"full": d_in * d_out, "lora": r * (d_in + d_out)}`.

4. Реализуйте `verify_equivalence()` / `verifyEquivalence()` — проверьте численно,
   что `(W + B@A) @ x` равно `W @ x + B @ (A @ x)` с точностью до 1e-9.

5. Реализуйте `param_savings_table()` / `paramSavingsTable()` — выведите таблицу,
   показывающую полное количество параметров и количество для LoRA, а также коэффициент экономии для d=512/1024/4096, r=4/8/16/64.

**Acceptance:**

- Проверка эквивалентности проходит (numpy `allclose` или ручная проверка абсолютной разницы).
- Таблица параметров выводится и показывает корректные значения.
- Никаких импортов ML-фреймворков (только numpy/обычные массивы).
- Вывод B@A равен точно нулю для свежеинициализированного LoRA (так как B=0).

**Files:**

- `ts/06-distillation.ts`

**Steps:**

1. Реализуйте `llm_label()` / `llmLabel()` — вызовите teacher-LLM с
   `max_tokens=5, temperature=0`, чтобы пометить каждый текст как `positive`, `negative`
   или `neutral`. Разберите ответ; при неожиданном выводе используйте `neutral` по умолчанию.

3. Реализуйте `student_predict()` / `studentPredict()` — kNN (k-ближайших соседей) по косинусному сходству: найдите top-k ближайших обучающих эмбеддингов, верните наиболее часто встречающуюся метку.
4. Реализуйте `evaluate()` / `evaluate()` — замерьте время работы студента и учителя на отложенной тестовой выборке; вычислите точность и задержку на запрос для каждого.

**Acceptance:**- `llm_label()` возвращает по одной метке для каждого текста; все метки входят в `["positive", "negative", "neutral"]`.
- `train_student()` создаёт `StudentClassifier` с одним embedding’ом на размеченный пример.
- `student_predict()` возвращает корректную метку для каждого тестового входа.
- `evaluate()` выводит таблицу с точностью и задержкой на каждый запрос для обеих моделей.
- Задержка студента заметно ниже, чем задержка учителя.
