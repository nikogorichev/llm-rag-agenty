# # Концепции

## # Квантование

Веса нейронной сети хранятся как числа с плавающей точкой. По умолчанию используется
fp32 (32 бита, 4 байта на вес). Квантование снижает точность, чтобы сэкономить память
и ускорить вычисления:

| Format         | Bits/weight | Relative size | Quality loss |
| -------------- | ----------- | ------------- | ------------ |
| fp32           | 32          | 1×            | baseline     |
| fp16 / bf16    | 16          | 0.5×          | negligible   |
| int8           | 8           | 0.25×         | small        |
| int4 (GGUF Q4) | ~4.5        | ~0.14×        | moderate     |
| int2           | 2           | 0.0625×       | significant  |

Ключевая идея: для инференса (не обучения) можно допустить небольшое снижение точности,
поскольку мы не накапливаем градиенты. Модель Q4 часто показывает результат в пределах 5% от fp16-модели
при 1/4 потребления памяти.

**GGUF** — формат файла, используемый llama.cpp. Он упаковывает квантованные веса
вместе с метаданными (словарь токенизатора, конфигурация архитектуры) в один переносимый
файл. Ollama использует GGUF под капотом.

## # KV-кеш

При авторегрессионной генерации модель обрабатывает все предыдущие токены, чтобы
предсказать следующий. Наивный подход означал бы пересчёт матриц ключей (K) и
значений (V) для каждого прошедшего токена на каждом новом шаге — O(n²) работы
для последовательности длиной n.KV-кэш хранит K и V для всех прошлых токенов, поэтому на каждом шаге нужно вычислять только K и V для НОВОГО токена. Это сокращает стоимость генерации каждого нового токена с O(n) до O(1) в слое внимания.

Почему длина контекста квадратична без кэширования:```
Without KV cache:  step t costs O(t) attention ops → total O(n²)
With KV cache:     step t costs O(1) new K/V + O(t) attention read → total O(n)
```Цена: память KV-кэша растёт вместе с длиной последовательности. Для модели 7B с контекстом в 4096 токенов KV-кэш может занимать несколько гигабайт. Именно поэтому inference с длинным контекстом стоит дорого, даже если веса модели фиксированы.

## # Throughput vs latency

- **Latency** (задержка): время до первого токена (TTFT) + время на один выходной токен (TPOT)
- **Throughput** (пропускная способность): токенов в секунду по ВСЕМ одновременным запросам

Эти показатели противоречат друг другу:

- Один запрос получает минимальную задержку, когда монополизирует GPU.
- Пропускная способность максимальна при **batching** (пакетировании): обработке нескольких запросов одновременно, что амортизирует фиксированные затраты на загрузку весов.

Модель конкурентности: отправка N запросов одновременно вместо последовательно показывает выгоду от пакетирования — суммарное время растёт значительно медленнее, чем N×время_одного.

## # Serving-движки

| Engine                | Best for                 | Key feature                           |
| --------------------- | ------------------------ | ------------------------------------- |
| **Ollama**            | Single-user local dev    | Одна команда, кроссплатформенность, GGUF     |
| **llama.cpp**         | Embedded / edge          | Минимум зависимостей, inference на CPU           |

Практическое правило: Ollama для локальных экспериментов, vLLM для массового продакшен-обслуживания.

## # Внутри serving-движка: continuous batching, PagedAttention, speculative decoding (заметки к собеседованию)

Три техники объясняют большую часть разрыва между «наивным циклом трансформера» и пропускной способностью уровня vLLM. На собеседованиях по LLM-инфраструктуре ожидают знание всех трёх:**Continuous batching (a.k.a. in-flight batching).** При статическом батчинге мы сначала собираем батч, затем выполняем его и возвращаем всё, когда завершается _самая длинная_ последовательность — короткие запросы простаивают в ожидании длинных. Continuous batching планирует выполнение на **уровне итераций**: после каждого шага декодирования завершённые последовательности покидают батч, а запросы из очереди присоединяются сразу. GPU загружен полностью, TTFT снижается, а пропускная способность на смешанном трафике (разной длины) возрастает в несколько раз. Это главный вклад vLLM/TGI; эксперимент с конкурентностью из Задания 3 — это то, что видит клиент как «тень» этого механизма.

**PagedAttention.** KV-кэш (Задание 5) — главный потребитель памяти, а наивные движки выделяют под каждый запрос один непрерывный кусок размером с его _максимально_ возможную длину — большая часть которого пропадает из-за внутренней фрагментации. vLLM применяет трюк виртуальной памяти: кэш разбивается на блоки фиксированного размера (**blocks (pages)**), таблица блоков на запрос отображает логические блоки в физические, блоки выделяются по требованию и освобождаются по завершении. Потери падают с ~60–80% до <4%, поэтому помещается гораздо больше последовательностей → бо́льшие эффективные батчи → та пропускная способность, которая нужна continuous batching. Бонус: общие префиксы (одинаковый системный промпт) могут указывать на одни и те же физические блоки — кэширование промптов с копированием при записи (copy-on-write).

**Speculative decoding.** Декодирование ограничено пропускной способностью памяти: на каждом шаге перемещаются все веса, чтобы произвести _один_ токен. Пусть маленькая **draft model** предложит k токенов дешево, а затем целевая модель проверит все k **за один параллельный прямой проход** — принять самый длинный префикс, с которым согласна целевая модель (плюс один исправленный токен). Правило отбора через rejection sampling делает распределение выхода **в точности** таким же, как у целевой модели — это без потерь, в отличие от квантования. Типичное ускорение декодирования в 2–3 раза, когда acceptance rate у draft-модели высока; деградирует изящно, когда нет. Варианты, которые стоит упомянуть: Medusa (дополнительные декодинговые головки вместо draft-модели) и n-gram/prompt-lookup drafting.

Резюме в одно предложение для собеседований: continuous batching не даёт GPU простаивать, PagedAttention позволяет делать батчи большими, speculative decoding сокращает латентность на токен — и все три технологии работают вместе.

# # Углубляемся

- [llama.cpp](https://github.com/ggerganov/llama.cpp) — эталонный движок для LLM-инференса, оптимизированный под CPU. Спецификация формата GGUF находится здесь.
- [vLLM docs](https://docs.vllm.ai) — объяснение PagedAttention и continuous batching. Значительно более высокий throughput при многопользовательском обслуживании.
- [Ollama](https://ollama.com) — самый простой способ запустить локальную модель; использует llama.cpp под капотом.
- ["Efficient LLM Inference" survey](https://arxiv.org/abs/2404.14294) — обзор по квантованию, speculative decoding, дистилляции и всему остальному в одной статье.
- [FlashAttention](https://arxiv.org/abs/2205.14135) — механизм внимания, учитывающий ввод-вывод и избегающий построения полной матрицы внимания; дополняет KV caching.
- [AWQ quantization](https://arxiv.org/abs/2306.00978) — квантование весов с учётом активаций; лучшее качество при 4 битах по сравнению с наивным округлением.

# # Переменные окружения```bash
# All tasks default to Ollama — no extra keys needed.
LLM_PROVIDER=ollama
OLLAMA_CHAT_MODEL=llama3.2           # default; change to llama3.2:1b for Task 2

# Task 3 concurrent benchmark (optional):
OLLAMA_BASE_URL=http://localhost:11434/v1   # default
```## Дополнительные возможности```bash
# For llama-cpp-python (local CPU inference without Ollama):
uv sync --extra llama-cpp
# Installs: llama-cpp-python (~200 MB wheel, or builds from source).
# On Mac with Apple Silicon, set: CMAKE_ARGS="-DLLAMA_METAL=on"
# before installing to enable Metal GPU acceleration.

# For vLLM (high-throughput GPU serving — Linux/CUDA only):
# vLLM is NOT available on Mac. Use it on a Linux server with an NVIDIA GPU.
# pip install vllm   (outside uv, system python)
```
