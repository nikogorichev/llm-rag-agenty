# Модуль 15 — Рассуждения и вычисления во время инференса

Обычные LLM (Large Language Models) отвечают сразу: один прямой проход, один выход.
Модели _рассуждения_ (reasoning models) и стратегии _вычислений во время инференса_ (test-time compute)
тратят дополнительные вычислительные ресурсы во время инференса — перед (или во время) возврата ответа,
обменивая задержку и стоимость на точность при решении сложных многошаговых задач.

В этом модуле мы сделаем этот компромисс наглядным: вы сравните обычную модель с моделью рассуждения,
самостоятельно реализуете самосогласованность (self-consistency) и сэмплирование best-of-N, построите
цикл самосовершенствования (self-refine) и, наконец, построите кривую «затраты/точность», чтобы решить,
когда дополнительные вычисления действительно оправданы.

# # Концепции

## # Что такое «модели рассуждения»?

Семейство моделей OpenAI o1/o3 и функция _расширенного мышления_ (extended thinking) от Anthropic
выделяют дополнительные вычислительные ресурсы на внутренние обсуждения перед тем, как выдать видимый результат.
Модель генерирует скрытый «черновик» цепочки рассуждений (chain-of-thought, CoT) и только затем выдаёт
финальный ответ.

Ключевые свойства:

- **Более высокая точность** на сложных задачах по математике, коду и многошаговой логике.
- **Более высокая задержка и стоимость** — скрытые токены всё равно стоят денег (часто с наценкой).
- **Меньшая управляемость** — вы не можете направлять внутренние рассуждения; только через prompt.
- **Не всегда лучше** — для простого поиска или одношаговых задач накладные расходы — это чистая трата.

## # Расширенное (адаптивное) мышление — Anthropic

Расширенное мышление Claude (`betas=["interleaved-thinking-2025-05-14"]`) позволяет модели
выдавать блоки `<thinking>`, видимые в необработанном ответе перед финальным ответом.
Вы управляете `budget_tokens`, чтобы ограничить бюджет скрытых рассуждений.
Доступ осуществляется напрямую через SDK (Software Development Kit) `anthropic` — обёртка `chat()`
в `llm_core` не открывает этот бета-параметр. Это намеренный урок «за рамками абстракций».

## # Модели рассуждения OpenAI (o1, o3, o4-mini)

Передайте `model="o4-mini"` (или `o1`, `o3-mini`) в SDK OpenAI.
Эти модели используют `max_completion_tokens` вместо `max_tokens`.
Нет стриминга для токенов рассуждения; в видимом `usage.completion_tokens_details` указано,
сколько токенов было потрачено на рассуждения по сравнению с видимым выводом.
Установите `reasoning_effort` (`"low"/"medium"/"high"`), чтобы настроить вычислительный бюджет.### Test-time compute БЕЗ reasoning-модели

Вы можете аппроксимировать поведение reasoning-модели с помощью любой стандартной модели:

| Стратегия                 | Механизм                                              | Стоимость       |
| ------------------------ | ------------------------------------------------------ | --------------- |
| **Deeper CoT**           | Более длинный промпт "think step by step"              | 1 × больше вывода |
| **Self-consistency**     | Сэмплить N раз, выбрать большинство                    | N × стоимость        |
| **Best-of-N + verifier** | Сэмплить N, оценить каждый через verifier LLM, выбрать лучший | ~2N × стоимость      |

Self-consistency и best-of-N особенно эффективны, когда вы можете написать недорогой
verifier (unit test, math checker, regex) — verifier — это секретное оружие.

## # Self-refine / reflection

Draft → critique → revise — это трёхходовый цикл, имитирующий то, как человек
проверяет свою работу. Даже одна итерация часто улучшает фактическую точность,
ясность и полноту на открытых задачах. Множественные итерации обычно сходятся быстро
(выигрыш от 3-й итерации редко оправдывает затраты на 2-ю).

## # Кривая «стоимость/задержка vs. качество»

Если отложить точность против вычислений (tokens × price), становится видно:

- Фаза резкого улучшения (переход от 0-shot к CoT или 1 проходу рассуждений).
- Плато, где дополнительные вычисления дают убывающую отдачу.
- Редкие регрессии при очень большом N (majority vote может усилить неверный ответ,
  если verifier или распределение сэмплирования смещены).

Понимание того, где ваша задача находится на этой кривой, — это инженерное решение.

# # Задания

## # Задание 1 🟢 — Reasoning vs стандартная модель

**Цель:** Отправить одну и ту же сложную многошаговую задачу в стандартную модель и в reasoning-модель. Сравнить корректность, количество токенов и реальную задержку (wall-clock latency) в параллельном режиме.

**Шаги:**

1. Откройте `py/01_reasoning_vs_standard.py` / `ts/01-reasoning-vs-standard.ts`.
2. Реализуйте `call_standard(question)` — используйте `get_provider("openai")` с `gpt-4o-mini` (или вашим провайдером по умолчанию).
3. Реализуйте `call_reasoning(question)` — используйте OpenAI SDK напрямую с `o4-mini` и `reasoning_effort="medium"`, ИЛИ используйте Anthropic SDK с `extended_thinking`.
4. Для каждой тестовой задачи вызовите обе модели, замерьте задержку и выведите таблицу сравнения.

**Критерии приёмки:**

- Обе реализации возвращают ответ для каждой тестовой задачи.
- Таблица содержит модель, ответ, входные токены, выходные токены, задержку (мс).
- Вы можете одной фразой объяснить, почему reasoning-модель показывает (или не показывает) лучший результат.

## # Задание 2 🟡 — Test-time compute без reasoning-модели

**Цель:** Реализовать self-consistency (семплирование N вариантов, мажоритарное голосование) и best-of-N с верификатором, чтобы повысить точность стандартной модели без перехода на reasoning-модель.

**Шаги:**1. Откройте `py/02_test_time_compute.py` / `ts/02-test-time-compute.ts`.
2. Реализуйте `self_consistency(question, n)` — сгенерируйте N завершений CoT при
   `temperature=0.8`, извлеките из каждого итоговый ответ, верните `majority_vote(answers)`.
3. Реализуйте простой `verify(question, answer)` — вызовите LLM с коротким промптом
   "Is this answer correct? Reply YES or NO.", используя temperature=0.
4. Реализуйте `best_of_n(question, n)` — сгенерируйте N ответов, прогоните их через верификатор,
   верните первый ответ, который верификатор одобрит (или используйте majority vote как запасной вариант).
5. Запустите все три стратегии (1-shot, self-consistency, best-of-N) на тестовых задачах
   и выведите точность и общее количество потраченных токенов.

**Acceptance:**

- `self_consistency` выполняет выборку ровно N раз и использует majority vote.
- `best_of_n` вызывает верификатор и возвращает одобренный ответ.
- Выходная таблица отображает стратегию, количество правильных/общее, потраченные токены.

## # Task 3 🟡 — Self-refine / reflection

**Goal:** Построить цикл черновик → критика → доработка; оценить, улучшается ли ответ на каждой итерации.

**Steps:**

1. Откройте `py/03_self_refine.py` / `ts/03-self-refine.ts`.
2. Реализуйте `draft(task)` — сгенерируйте исходный ответ.
3. Реализуйте `critique(task, draft_text)` — попросите модель "What is wrong or missing
   in this answer? Be specific and list issues." Верните текст критики.
4. Реализуйте `revise(task, draft_text, critique_text)` — попросите модель улучшить
   ответ, учитывая критику. Верните доработанный текст.
5. Запустите цикл на `MAX_ITERATIONS` (по умолчанию 2), выводя каждый черновик → критику → доработку.
6. Сравните исходный черновик с финальной доработкой по критериям (длина, конкретика, любые
   фактические изменения). Даже простая проверка "изменилось ли что-то?" — допустимое начало.

**Acceptance:**

- Каждая итерация создаёт видимую критику и доработанный ответ.
- После `MAX_ITERATIONS` финальный ответ выводится рядом с исходным черновиком.
- Вы можете наблюдать (и описать) хотя бы одно конкретное улучшение в доработанном варианте.
