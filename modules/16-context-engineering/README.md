# Модуль 16 — Контекстная инженерия

Контекстное окно не безгранично — это ограниченный и оплачиваемый ресурс. Каждый токен на входе стоит денег и времени; каждый исключённый токен — это информация, недоступная для модели. _Контекстная инженерия_ — это искусство тратить этот ресурс разумно.

По завершении этого модуля вы научитесь точно подсчитывать количество токенов, кешировать длинный повторяющийся префикс для экономии, уплотнять длинные диалоги, чтобы избежать переполнения, применять MapReduce к документу, который не помещается в один вызов, отправлять пакет запросов со скидкой и выносить громоздкие результаты инструментов из истории сообщений цикла агента.

---

# # Концепции

## # Контекстное окно как бюджет

Контекстное окно — это максимальное количество токенов (вход + выход вместе), которые модель может обработать за один вызов. Типичные размеры в 2025 году:

| Model            | Context |
| ---------------- | ------- |
| gpt-4o-mini      | 128 K   |
| claude-haiku-4-5 | 200 K   |
| claude-opus-4-8  | 200 K   |
| gemini-1.5-pro   | 1 M     |

Превышение лимита приводит к ошибке или тихому усечению. Вы отвечаете за управление лимитом. Лимит включает вход и выход, поэтому длинный системный промпт оставляет меньше места для документа пользователя.

## # Подсчёт токенов

Токены — это подсловные единицы, выдаваемые токенизатором. Практическое правило: 1 токен ≈ 3–4 английским символам. Для точного подсчёта:

- Python: `tiktoken` (для моделей OpenAI); `client.beta.messages.count_tokens()` из Anthropic SDK.
- TypeScript: `@dqbd/tiktoken` (WASM-порт tiktoken); `.beta.messages.countTokens()` из Anthropic SDK.

Подсчёт перед отправкой запроса позволяет соблюдать бюджет и выбирать стратегию усечения.

## # Кеширование промптов

При повторных вызовах с большим неизменным префиксом (длинный системный промпт, большой документ, определения инструментов) обычно каждый раз списывается полная стоимость входа. Кеширование промптов позволяет это избежать:- **Anthropic** — отмечайте точки разбиения кэша в списке сообщений через `cache_control: {"type": "ephemeral"}`.
  Попадание в кэш видно в `usage.cache_read_input_tokens`. TTL кэша — 5 минут.
- **OpenAI** — кэширование автоматически включается для входов длиннее 1024 токенов. Дополнительные параметры не требуются.
  Чтение из кэша отражается в `usage.prompt_tokens_details.cached_tokens`.

Оба провайдера взимают за попадание в кэшь лишь часть от обычной цены входных токенов (часто 10–20 % от полного тарифа). Это функция _по ту сторону абстракции_: нужно использовать провайдерские SDK (Software Development Kits) напрямую.

**Учёт порядка сообщений для кэша.** Prompt caching работает _по префиксу_: запрос попадает в кэш только для самого длинного непрерывного фрагмента токенов, который в точности совпадает с началом предыдущего запроса.
Переписывание ранних сообщений в середине диалога — очистка старых ходов, инлайн‑вставка новой системной инструкции в начало или изменение порядка сообщений — меняет этот префикс, нарушает стабильность префикса и уничтожает все попадания в кэш с этого момента. Правильный шаблон — **append-only история** (история только с добавлением в конец): оставляйте всё уже отправленное байт‑в‑байт нетронутым и добавляйте новые инструкции в КОНЕЦ списка сообщений. Именно поэтому платформы для агентов сохраняют каждый старый промпт в качестве точного префикса следующего — запрос хода N — это запрос хода N−1 плюс несколько добавленных сообщений, так что всё общее префиксное содержимое читается из кэша, а не отправляется заново по полной цене.

## # Память беседы / уплотнение

В длинном чате контекстное окно заполняется старыми ходами. Два стандартных способа смягчить это:

1. **Скользящее окно** — хранить только последние K ходов (просто; полностью теряет старый контекст).
2. **Текущее резюме** — когда диалог превышает бюджет токенов, суммировать самые старые ходы в короткий абзац, заменить их этим резюме и продолжить. Модель сохраняет суть без полной дословной истории.

Гибридный подход («хранить последние K ходов И текущее резюме всего, что старше») наиболее надёжен.

## # Выгрузка результатов toolsСжатие ориентировано на диалоги; в циклах агентов есть более серьёзный источник расхода: **результаты инструментов**. В многоитерационном цикле агента (паттерн ReAct из модуля 06) один результат веб-поиска или чтения файла может занимать 3–4 K токенов — а поскольку вся история перепосылается на каждой итерации, эти токены оплачиваются снова на _каждом следующем шаге_. Через пять итераций после одного поиска в 4 K токенов этот результат обойдётся примерно в 20 K входных токенов, причём большая часть из них никогда не нужна дословно.

Паттерн выгрузки (offloading) разрывает этот круг:

1. **Сохранить** полный вывод инструмента в _хранилище логов инструментов_ (словарь, файл, строку БД) с ключом по id.
2. **Сослаться** на него в истории однострочным заполнителем — например, `[Tool Log #3] web_search output stored (3 812 tokens); call read_tool_log(3) to retrieve` — желательно с коротким предварительным просмотром, чтобы модель понимала, что там находится.
3. **Получать по запросу** через инструмент `read_tool_log(id)`, который агент может вызывать, только когда ему действительно нужен полный контент.

Теперь контекст растёт примерно на 50 токенов за вызов инструмента вместо тысяч, и ничего не теряется — хранилище точно возвращает выводы. Это становится _необходимостью_ (а не просто приятной опцией), как только циклы становятся длинными: 10 итераций × несколько крупных результатов инструментов переполнят даже окно в 200 K, а перечитывание мегабайтов устаревшего вывода инструментов ухудшает качество («потеря в середине», lost in the middle) и увеличивает стоимость. Claude Code и подобные системы для работы с агентами делают именно это для больших результатов инструментов. В задании 6 вы это реализуете.

## # Стратегии работы с длинным контекстом

Даже при окне контекста в 200 K попытки уместить весь корпус расточительны и часто снижают качество.

**Map-reduce:**

1. _Map_: обработать каждый чанк независимо (извлечь, суммировать, ответить).
2. _Reduce_: объединить результаты чанков в финальный ответ.

**Refine:**

1. Обработать чанк 1 → промежуточный ответ.
2. Обработать чанк 2 + промежуточный ответ → обновлённый ответ.
3. Повторить для всех чанков.

**Lost in the middle (потеря в середине):** LLM (большие языковые модели) лучше запоминают информацию в начале и в конце контекста, чем в середине. Размещение самого важного контента в начале (или в конце) даёт лучший результат, чем размещение его посередине.

## # Batch APIBatch API (Application Programming Interface) позволяет отправить сотни запросов одним вызовом API, которые обрабатываются асинхронно
(обычно в течение 24 часов). Взамен провайдеры обычно взимают 50 % от цены онлайн-режима.
Лучше всего подходит для: прогонов оценок (eval runs), пайплайнов извлечения данных, массового суммирования — любой нагрузки, которая не чувствительна к задержкам.

- **OpenAI**: `client.batches.create(...)` с файлом JSONL (JSON Lines) запросов. Проверяйте статус через `client.batches.retrieve(id)`.
- **Anthropic**: `client.beta.messages.batches.create(...)`. Проверяйте статус через `client.beta.messages.batches.retrieve(id)`.

Это выходит за рамки абстракции `llm_core` — используйте SDK напрямую.

**Goal:** Подсчитывать токены точно; вписывать prompt в токенный бюджет; сравнить стратегии усечения.

**Steps:**

- `count_tokens` использует tiktoken, а не приближённый подсчёт слов.

## # Задача 4 🟡 — Long-context strategies

**Цель:** применить map-reduce и refine к документу, который слишком велик для одного вызова; пронаблюдать эффект «потеря в середине».

**Шаги:**1. Откройте `py/04_long_context.py` / `ts/04-long-context.ts`.
2. Сгенерируйте или загрузите длинный документ (минимум 4 чанка по ≥ 500 токенов каждый).
   Константа `LONG_DOCUMENT` в заготовке достаточна.
3. Реализуйте `split_into_chunks(text, max_tokens_per_chunk)` — разбиение по `count_tokens`.
4. Реализуйте `map_reduce(chunks, question, llm)`:
   - _Map_: для каждого чанка запросите "Based on this excerpt, answer: {question}" — соберите мини-ответы.
   - _Reduce_: объедините все мини-ответы в финальный ответ ещё одним вызовом LLM.
5. Реализуйте `refine(chunks, question, llm)`:
   - Начните с пустого промежуточного ответа.
   - Для каждого чанка отправьте: interim + chunk + question → обновлённый interim.
   - Верните финальный interim.
6. Продемонстрируйте эффект "lost in the middle": поместите уникальный факт (имя, число) в первый чанк,
   средний чанк и последний чанк. Задайте модели вопрос обо всех трёх. Выведите точность воспроизведения.

**Acceptance:**

- `split_into_chunks` создаёт чанки размером не более `max_tokens_per_chunk`.
- `map_reduce` и `refine` оба возвращают связный финальный ответ.
- Демонстрация lost-in-the-middle показывает, какое расположение (первое/среднее/последнее) вспоминается наиболее надёжно.

Полностью офлайн и детерминированно — предоставлен скриптовый цикл агента из 5 итераций с заглушкой инструмента `web_search`; провайдер и API-ключ не нужны.

**Файлы:** `py/06_tool_offloading.py` / `ts/06-tool-offloading.ts`

**Шаги:**

1. Откройте файл и изучите подготовленные части: фейковый `web_search` (большие заранее подготовленные полезные нагрузки, в одной из которых скрыта строка `FINDING:`), скриптовый 5-итерационный `SCRIPT` и наивный базовый вариант `run_loop_naive` / `runLoopNaive`, который добавляет в историю полный результат каждого инструмента.

5. Реализуйте `run_loop_with_offloading(script, store)` — скопируйте логику наивного цикла, но добавляйте ссылки вместо полных результатов, а полный лог извлекайте через `read_tool_log` только тогда, когда это требуется скриптом.

**Приёмка:**- Для обоих циклов выводится количество токенов контекста на каждой итерации: наивный контекст монотонно растёт и превышает 9 000 токенов, тогда как контекст с выгрузкой остаётся ниже 1 200 токенов на каждой итерации.
- `read_tool_log` возвращает исходный payload без изменений, а в хранилище содержатся последовательные id 1, 2, 3.
- Финальный ответ запуска с выгрузкой содержит факт-«иглу», который существует только внутри сохранённого payload — доказательство того, что извлечение по запросу сработало.
- Скрипт выводит сообщение "All acceptance checks passed."
