# # Концепции

## # Цикл eval```
New prompt/model idea
        │
        ▼
1. Run it against the versioned eval set  (task 1)
        │
        ▼
2. Compare it to the current baseline     (task 2 — experiments)
        │
        ├── better?  → promote to baseline, merge into eval set
        │
        └── worse?   → reject; CI gate catches it if it slips (task 3)
                               │
                               ▼
                 3. Low-confidence cases → human review queue (task 4)
                               │
                               ▼
                 4. Human labels feed back into eval set (task 4 --merge)
                               │
                               ▼
                 5. Production logs monitored for drift (task 5)
```### Зачем версионировать набор для оценки?

Набор для оценки, который можно менять по своему усмотрению, — это не набор для оценки, а черновик. Зафиксируйте его в git. Используйте поле версии (`"version": "1.0.0"`). При добавлении новых кейсов (например, из очереди ручной проверки) увеличивайте patch. Любой файл прогона фиксирует, против какой версии оценивания проводился скор, чтобы результаты всегда можно было воспроизвести.

## # Спектр оценивающих моделей

| Оценивающая модель | Скорость | Стоимость           | Когда использовать               |
| ------------------ | -------- | ------------------- | --------------------------------- |
| Точное совпадение  | мгновенно | бесплатно          | Структурированные выводы, код, ID |
| Contains           | мгновенно | бесплатно          | Ключевые термины, которые должны присутствовать |
| LLM-as-judge       | секунды  | ~$0.001/кейс        | Свободная генерация, нюансы       |

Используйте все три слоя: точное совпадение там, где можно, и LLM (Large Language Model) для остального. Скор от LLM-судьи также даёт сигнал уверенности для очереди ручной проверки (задача 4).

## # Регрессионные ворота в CI

Ворота — это просто скрипт, который завершается с ненулевым кодом выхода, когда метрика опускается ниже порога. GitHub Actions трактует ненулевой код выхода как сбой сборки — больше ничего не требуется. Тот же скрипт можно запустить как pre-push хук Husky, чтобы инженеры ловили регрессии до отправки кода.

**Важный порог для установки:** faithfulness (оценка от LLM-судьи на отложенных RAG (Retrieval-Augmented Generation) кейсах). Падение faithfulness обычно означает, что изменение промпта заставило модель игнорировать контекст и начать галлюцинировать.

## # Ручная проверка + петли обратной связи

LLM-судьи хороши, но не идеальны. Для выводов с низкой уверенностью (оценка судьи ниже ~0,75) ставьте их в очередь на ручную проверку. После того как человек помечает вывод как правильный, он становится новым «золотым» примером в наборе для оценки. Это маховик: больше продакшен-трафика → больше меток → лучше набор для оценки → более точные измерения.

## # Мониторинг в продакшене

Мониторинг отличается от оценки: оценка измеряет _качество_; мониторинг измеряет _здоровье_. Отслеживайте:- **Latency** (p50, p95) — пики p95 означают проблемы с хвостовой задержкой.
- **Error rate** — резкие скачки говорят об сбоях провайдера или ошибках переполнения контекста.
- **Cost** — неожиданно дорогие вызовы указывают на раздувание промпта или неправильную конфигурацию модели.
- **Token usage** — постепенный рост числа входных токенов сигнализирует об ошибках накопления контекста.

Формат логов JSONL (JSON Lines) из задания 2 модуля 07 напрямую поступает на вход монитору в задании 5.

## # Drift: почему модель, прошедшая оценку, всё равно деградирует (заметки к собеседованию)

«Производительность модели в продакшене упала, но вы ничего не меняли — что произошло?» — стандартный вопрос на собеседованиях по MLOps. Основные термины:

- **Data drift (covariate shift)** — смещается распределение входов `P(x)`: появляются новые темы, новые сегменты пользователей, новый формат документов в RAG-корпусе. Модель не менялась, но всё чаще отвечает на вопросы из внеобучательного распределения.
- **Concept drift** — смещается отношение «вход→выход» `P(y|x)`: правильный ответ изменился (цены, политики, API), в то время как корпус или модель остались заморожены. Устаревший RAG-корпус — это concept drift, созданный вами самими.
- **Upstream/model drift (специфично для LLM)** — хостинг-провайдер молча обновляет модель за псевдонимом вроде `-latest`, или изменение промпта/инструмента смещает поведение. Тот же набор для оценки, другая модель → другие результаты.

Обнаружение drift’а — это сравнение распределений между эталонным окном (что представляет набор для оценки) и текущим окном:

- **Числовые сигналы** (latency, количество токенов, оценки confidence/оценки judge): сравниваем гистограммы — PSI (Population Stability Index) или критерий KS; PSI > 0.2 — общепринятый порог «требуется расследование».
- **Текстовые входы**: делаем embeddings для обоих окон (модуль 04) и сравниваем — косинусное расстояние между центроидами или доля запросов из текущего окна, у которых ближайший сосед в эталоне ниже порога сходства. Рост расстояния = пользователи спрашивают о том, чего ваш набор для оценки не покрывал.
- **Выходы**: отслеживаем динамику оценок judge и частоту отказов во времени (отчёт из задания 5 — естественное место для этого); резкое изменение без деплоя — это upstream drift.План действий: data drift → добавить новые входные данные в eval-сет (обратная связь из задачи 4) и перенастроить поиск; concept drift → обновить корпус / переразметить данные; upstream drift → зафиксировать версии моделей и повторно прогнать регрессионные ворота (задача 3) при каждом изменении фиксации.

# # Углубляемся

- **Langfuse**: open-source платформа для оценки и наблюдаемости с UI (пользовательским интерфейсом) для ручной проверки, датасетами и дашбордами с оценками. Всё в этом модуле напрямую отображается на концепции Langfuse (datasets = eval sets, traces = записи логов, scores = результаты оценивания, human annotations = метки из задачи 4).
- **Семантическое версионирование для оценок**: относитесь к вашему eval set как к библиотеке. Критические изменения (удаление случаев, изменение рубрик) требуют повышения мажорной версии. Новые случаи — патчи. Зависимые системы закрепляются за `v1.x`, чтобы избежать неожиданностей.
- **Консенсус нескольких судей**: запускайте две разные LLM в роли судьи и отмечайте случаи, где они расходятся во мнениях (разница оценок > 2), как «неопределённые» → в очередь для человека.
- **Online evals**: оценивайте каждый производственный вызов в реальном времени с помощью быстрой модели-судьи, отправляя оповещения, когда качество падает ниже базовой линии. Добавляет задержку (~1 с дополнительно), но даёт живой сигнал о качестве.
- **Регрессионное тестирование промптов с помощью `git bisect`**: сохраняйте теги с результатами оценок в git вместе с файлами промптов, которые их породили; `git bisect` может найти коммит, который сломал корректность (faithfulness).
