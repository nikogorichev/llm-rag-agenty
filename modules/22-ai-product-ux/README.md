# Модуль 22 — UX AI-продуктов

> **Метки глубины** 🟢 уровень приложения · 🟡 собрать одну деталь вручную

Создание LLM (большой языковой модели), которая может отвечать на вопросы, — уже норма. Сделать так, чтобы LLM выглядела **надёжной и удобной** — чтобы пользователи понимали, когда ей доверять, видели, откуда она взяла информацию, и могли возразить, когда она ошибается, — вот настоящая сложная продуктовая задача.

В этом модуле мы создаём небольшой, но полностью рабочий чат-интерфейс (UI — User Interface) и бэкенд для RAG (Retrieval-Augmented Generation), который его обеспечивает. Каждый принцип доверия и UX воплощён в работающем коде, который можно запустить и изучить.

# # Концепции

## # Почему UX важен для доверия к ИИ

Модель, которая права в 85 % случаев, бесполезнее, чем отсутствие модели, если пользователь не может понять, какие 15 % нужно игнорировать. Задача UX (User Experience) — показать неопределённость модели, раскрыть её рассуждения и дать пользователям способ её исправить.

Пять паттернов, отличающих демо от надёжного продукта:

| Паттерн            | Какую проблему решает                                                   |
| ------------------- | ----------------------------------------------------------------------- |
| **Стриминг**        | Долгое ожидание воспринимается как сбой. Токены, приходящие мгновенно, создают ощущение живости. |
| **Цитаты**          | «Откуда это взялось?» — пользователи не будут доверять тому, что не могут проверить. |
| **Уровни уверенности** | Ответам с низкой уверенностью нужно предупреждение, а не молчаливая выдача. |
| **Обратная связь**  | Пользователям нужен способ возразить. Каждый случай «выглядит неверно» — это обучающие данные. |
| **Потоки подтверждения** | Рискованные действия ИИ (отправка e-mail, удаление данных) должны быть ограничены. |

## # Стриминг (SSE)

Server-Sent Events (SSE) — правильный транспорт для стриминга токенов:

- Однонаправленный сервер → клиент (проще, чем WebSocket).
- Работает поверх обычного HTTP (HyperText Transfer Protocol) без специальной настройки.
- Клиент читает `text/event-stream` с помощью `EventSource` или `fetch` + `ReadableStream`.

Каждое SSE-событие в этом модуле — это типизированный JSON (JavaScript Object Notation) payload:```
data: {"type": "token",    "text": "..."}
data: {"type": "citation", "doc": {...}}
data: {"type": "done",     "confidence": 0.85}
data: {"type": "error",    "message": "..."}
```Типизированные события позволяют клиенту корректно обрабатывать каждое состояние без ненадёжного парсинга строк.

## # Цитаты / "показать источники"

LLM получает инструкцию выводить блок с цитатами в конце своего ответа:```json
{ "citations": ["doc1", "doc3"] }
```Сервер удаляет это из потокового текста, сопоставляет идентификаторы документов с полными метаданными и отправляет их как события `citation`. Клиент отрисовывает чипы, которые открывают панель с подробностями по источнику, позволяя пользователям проверить любое утверждение.

Это самая важная функция для доверия. Пользователи прощают неверные ответы, которые можно проверить; они не прощают неверные ответы без источника.

## # Уровни уверенности и состояния ошибок

У каждого ответа есть явный показатель уверенности. Клиент отображает:

- **Высокий (≥ 75%)** — зелёный значок, можно продолжать.
- **Средний (50–74%)** — жёлтый значок, «проверьте источники».
- **Низкий (< 50%)** — красный значок, заметное предупреждение.

Явное состояние ошибки (не просто запись в консоль) с кнопкой повторной попытки охватывает сетевые сбои и ошибки провайдера. Пустое состояние (до первого вопроса) — это третье отдельное состояние, а не пустая страница.

## # Сбор обратной связи

Каждый лайк/дизлайк и отчёт «выглядит неверно» отправляются как POST‑запрос на `/feedback` и сохраняются в формате JSONL (JSON Lines). Этот лог напрямую поступает в очередь ручной проверки из модуля 21, замыкая продуктовой цикл: плохие результаты в проде → разметка человеком → лучший набор для оценки → лучшая модель.

## # Проверка рискованных действий

Когда AI‑агент хочет выполнить действие с последствиями (отправить письмо, удалить запись, совершить покупку), требуйте явного подтверждения от пользователя:

1. Сервер выдаёт одноразовый токен подтверждения (`/actions/request`).
2. Клиент показывает модальное окно с описанием действия и полезной нагрузкой.
3. Пользователь одобряет или отклоняет (`/actions/approve`).
4. Токен истекает через 120 секунд, даже если не использован.

Этот шаблон обязателен для любого агентского действия с побочными эффектами. Это разница между AI, который помогает, и тем, который создаёт инциденты.

# # Обзор UI

## # Empty state

Откройте страницу до того, как задать вопрос. Вы увидите центрированный плейсхолдер с примерами вопросов — а не пустое белое поле.

## # Loading state

Отправьте вопрос. Сразу появится спиннер с надписью "Thinking…" — пользователь понимает, что процесс идёт.

## # Streaming (task 1)

Токены поступают по одному в карточке ответа. Мигающий курсор показывает, что поток активен. Посмотрите во вкладке Network → `/ask/stream` → Response, чтобы увидеть исходные SSE-события.

## # Citations (task 2)

После последнего токена под ответом появляются плашки с источниками ("Sources: Module 05 — RAG Module 07 — Advanced & Production"). Нажмите на плашку, чтобы открыть боковую панель источника с названием, URL и отрывком текста. Нажмите на оверлей или ✕, чтобы закрыть её.

## # Confidence (task 3)

В левом верхнем углу карточки ответа появляется цветной бейдж. Зелёный = высокий, жёлтый = средний, красный = низкий. В бейдже для ответов с низкой уверенностью добавляется текст "verify sources".

## # Error state (task 3)

Остановите бэкенд и отправьте вопрос. Появится состояние ошибки с сообщением о сетевой ошибке и ссылкой "Try again".

## # Feedback (task 4)

Нажмите 👍 или 👎 — на 3 секунды появится зелёное подтверждение "Thanks for your feedback!". Нажмите "This looks wrong", чтобы раскрыть текстовое поле; отправка сообщения отправляет rating="wrong" с заметкой на `/feedback`. Проверьте `feedback.jsonl` для подтверждения.

## # Approval flow (task 5)Нажмите «⚠ Simulate a risky action (requires approval)» в нижней части карточки ответа. Появится модальное окно с описанием действия и JSON-полезной нагрузкой. Нажмите Approve → сервер записывает это в `actions.jsonl` и подтверждает. Нажмите Cancel → сервер помечает действие как отклонённое. Не отвечайте в течение 2 минут → токен истекает.

## # Task 5 — Approval flow для рискованных действий 🟡

**Цель:** Модальное окно предотвращает побочные эффекты, инициированные ИИ, без подтверждения пользователя.

**Шаги:**1. Нажмите «⚠ Simulate a risky action» — появится модальное окно.
2. Одобрите — проверьте в `actions.jsonl` наличие `"approved": true`.
3. Отклоните — проверьте наличие `"approved": false`.
4. Расширьте бэкенд: после одобрения реально выполните побочный эффект. Начните с чего-нибудь безопасного и наблюдаемого: запишите файл, залогируйте в отдельный файл или выведите сообщение на стороне сервера.
5. Добавьте второе симулированное рискованное действие: «summarize-and-email» с payload `{"to": "test@example.com", "subject": "AI Summary"}`.
   В модальном окне адрес электронной почты должен быть хорошо виден — пользователи должны видеть точно, что произойдёт.
6. Проверьте истечение токена: на сервере измените TTL (Time To Live) на 5 с; запросите действие,
   подождите 6 с, затем одобрите — вы должны получить `"status": "expired"`.

**Критерии приёмки:**

- Модальное окно показывает название действия и JSON-полезную нагрузку.
- При одобрении и отклонении запись добавляется в `actions.jsonl`.
- Истёкшие токены возвращают `"status": "expired"` (не ошибку).
